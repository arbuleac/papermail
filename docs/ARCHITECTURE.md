# SuperSparrow architecture

SuperSparrow is a local-first Mac mail client. Every interaction is a read or write against a local SQLite store; the network never sits between a keystroke and a pixel. This document is the contract every module is built against.

## Product scope for v1

Sparrow's shape, Superhuman's speed:

- Unified inbox across Gmail and Microsoft accounts, with a thin rail: the views as folder tiles at the top, the accounts at its foot to narrow to one account.
- Views: Inbox, Starred, Sent, Drafts, Trash, All mail, and Later while something is snoozed. No folders, no labels, ever shown.
- The inbox always shows all of its mail. Gmail's Primary category and Outlook's Focused Inbox are stored (`inbox_section`) only to round-trip provider state; nothing filters or marks rows by them.
- Read conversations as stacked cards; quoted text folded; inline images; attachments with Quick Look.
- Actions: archive, mark read/unread, star, trash, restore, snooze (Later: archived now, back in the Inbox at a time; "Later" below), and unsubscribe from a mailing list (the link beside the sender, ⇧⌘U), which archives the conversation too, or ends its snooze. Undo for every action taken in the window (an unsubscribe's undo brings the conversation back; the request stays sent). Rows dragged onto the rail's folders take the same actions: Inbox moves them to the inbox, Trash trashes, Starred stars, All Mail archives; Sent, Drafts, Later and the accounts take nothing, and a drop that would change nothing the list shows is refused.
- Reply, reply all, forward, new message. Plain composer: bold, italic, underline, links, lists, quotes, attachments. A signature per account, set in Settings › Accounts. Undo send (five seconds). Send and Archive, the default: a reply or forward archives the conversation it answers as it is queued, and undoing the send brings it back ("Send and Archive"). `mailto:` links from other apps open a new message; Settings › General makes SuperSparrow the default mail app.
- Full-text search over subject, participants, and body (the snippet until the body is downloaded), as you type, with operators typed into the same field (`from:`, `to:`, `subject:`, `is:unread`, `is:read`, `is:starred`, `has:attachment`, `before:`, `after:`, `in:` a view, quoted phrases, a leading minus; "Search"). When the local results end, the list offers to search the server for more ("Server search").
- Keyboard first: `j`/`k` move, `e` archive, `l` snooze, `s` star, `u` unread, `#` trash, `r` reply, `a` reply all, `f` forward, `c` compose, `/` search, `⌘1`..`⌘9` switch account, `⌘0` unified.
- Unread badge on the Dock icon. New-mail notifications; one for a single conversation offers Archive, Mark as Read and Reply, and the summary of several offers none.
- A bounded store: Settings › General › Keep mail on this Mac (Everything, 1 year, 3 months) with the mailbox's size beside it; older mail keeps its row and searchable text and fetches its full message when opened ("Storage bounds").
- Calendar invitations: a message that carries one opens with a card (title, when, where, organizer, guests), its body folded under it, answered with Accept · Tentative · Decline, and Open in Calendar hands the invitation to the Mac's Calendar ("Calendar invitations"). It answers; it never becomes a calendar.

Out of scope for v1: rules, send later, S/MIME, server drafts, on-premises Exchange, IMAP, multiple windows beyond compose. What comes after v1, and in what order, is `docs/ROADMAP.md`.

## Modules

```
SSDesign (Quire tokens, components)
        ▲ draws with
SuperSparrowApp (AppKit, WebKit)  ──reads──▶  MailStoring (SQLite)  ◀──writes──  SyncEngine (actors)
        │ commands                                                                   │
        └──────────────▶  MailClient (facade)  ─────────────────────────────────────┘
                                                                                      │
                                                                  MailProvider ◀──────┘
                                                               ┌──────┴──────┐
                                                        GmailProvider    GraphProvider
                                                               └──────┬──────┘
                                                          AccessTokenProvider (OAuth, Keychain)
```

- **SSCore/Model**: value types shared by everything. Already written; change only by agreement.
- **SSCore/Ports**: `MailProvider`, `MailStoring`, `MailClient`, `TokenStore`, `AccessTokenProvider`, sanitizer output. Already written.
- **SSCore/Store**: `SQLiteMailStore: MailStoring` using GRDB `DatabasePool` (WAL). Schema in `docs/DATA-MODEL.md`.
- **SSCore/Sync**: `AccountSyncer` (two lanes per account: the `LiveLane` actor owns the change cursor, replays the outbox and polls; the `BackfillLane` actor downloads older mail and missing bodies behind it), `QuotaBudget` (one per account, paces the backfill by `ProviderQuota`, see "Quota budget"), `OperationRunner` (outbox replay), `SendRunner` (undo window then send), `SnoozeRunner` (brings snoozed conversations back at their time, "Later"), `Hydrator` (bodies: a live path for new mail, a paced path for the backfill, on-demand fetches), `AttachmentCache` (attachment files on disk, at most 1 GB; a miss downloads through the provider into a partial file in one folder, swept before a run's first download since an interrupted run leaves its files there, charged as live spend, and concurrent callers share the download and its progress through an `AttachmentProgressRelay`), `StorageSweeper` (the Keep mail window and the store's housekeeping, see "Storage bounds"), `ServerSearcher` (a search of the server for mail this Mac lacks, see "Server search"), `MailEngine: MailClient` (facade wiring these together).
- **SSCore/Transport**: what both providers' transports share for downloads: `HTTPDownload` (one request whose 2xx body is written to a file as it arrives, through a data task with a task delegate, so a test session's stub `URLProtocol` drives it; an error reply's body comes back in memory for the transport's own status mapping) and `DownloadProgressMeter` (bytes into fractions that only rise and stop at 0.99 until the caller says the file is complete; measured against Content-Length unless the body is compressed, otherwise against the caller's estimate, and silent with neither).
- **SSCore/Auth**: `OAuthFlow` (PKCE, loopback redirect on 127.0.0.1, system browser), `KeychainTokenStore: TokenStore`, `TokenManager: AccessTokenProvider`, `ClientConfigurationStore` (reads `oauth-clients.json`).
- **SSCore/Render**: `HTMLSanitizer` producing `SanitizedBody` with SwiftSoup, plus `QuoteDetector` and `TextExtractor`.
- **SSCore/Calendar**: our own small iCalendar reader and writer ("Calendar invitations"): `CalendarInvitationReader` (an invitation's facts out of iCalendar text), `RecurrenceRule` (a repeat rule in words, never expanded), `CalendarTimeZones` (IANA, vendor-prefixed and Windows zone names), `InvitationCalendarWriter` (the iMIP reply, and a calendar file written from facts).
- **SSGmail**: Gmail REST API client. Bootstrap = `users.messages.list` newest first with `-in:spam -in:trash -in:chats` (chats are hidden from All mail in Gmail too), hydrated via batch `messages.get?format=metadata` (the address, subject, date and threading headers, plus `List-Unsubscribe` and `List-Unsubscribe-Post`, which cost nothing more: a get is priced per call) in batches of 10 parts: a part costs 20 units, so a batch is 200 units rather than 1,000 of the 6,000 a user may spend a minute. Throttled parts (429, or 403 `rateLimitExceeded`/`userRateLimitExceeded`) are sent again on their own after the largest part's Retry-After (or the refill time Google names), otherwise after 1, 2 and 4 s, keeping the parts already answered; such a wait is sat out inline up to 60 s once the call has fetched messages, and with nothing fetched yet a wait over 10 s is reported at once. A Retry-After over 60 s, or parts still throttled after the schedule, raise `ProviderError.throttled`, which discards that call's fetched messages. 404 parts are skipped, other failed or unanswered parts are fetched one by one, and a 401 part refreshes the token and resends the batch. A message that fails on its own even then (a 400 or 500, a 403 that is not a rate limit, a reply that does not decode) is left out and reported unreadable (`lookUpMetadata(for:)`) rather than thrown, so it never fails a changes call after its history was paged (holding the cursor on every poll), a bootstrap, a backfill page or a search; a changes call keeps what the store has for it, since only a 404 says Gmail no longer has a message. The network, a throttle or a refused token on that fetch still fails the call. A reconcile lists the ids of Trash and Spam apart (`mailOutsideEnumeration`: `in:trash OR in:spam` with `includeSpamTrash`, 500 ids a page) so its sweep keeps what the enumeration leaves out but the store holds. The backfill listing (`backfillListing(page:limit:)`) is one `users.messages.list` call with the same `q` and `maxResults` as bootstrap, ids only (5 units a page); a bootstrap page token continues it. Gmail's per-user quota refusals carry no Retry-After header, so the refill time is read from "Retry after <RFC 3339>" in Google's error message; a time already past counts as unknown (nil). Each throttled response, or group of batch parts, is logged once at notice in the "gmail" category: HTTP status, Google's reasons and status, the request kind and the retry time public, the message text private. Changes = `users.history.list` from the `historyId` captured by `users.getProfile` before the head page; the live lane stores it as the cursor right after that page, not when the enumeration ends. Bodies via `messages.get?format=full`, MIME tree walked for text/html, text/plain, attachments and inline parts; the list headers are read from it too, so a message stored before the metadata asked for them learns them when its body is fetched again. Attachments the user opens (`downloadAttachment`) stream: the `messages.attachments.get` reply, a JSON object whose `data` is the file in base64url, is written to a file beside the cache's partial file as it arrives (`GmailHTTPClient.download`: the same token retry, status mapping and throttle log as every other request), then `GmailAttachmentDecoder` maps that file, finds the top-level `data` string and decodes it a slice at a time into the attachment cache, so neither the reply nor the file sits in memory whole. Its progress counts the reply's bytes against its Content-Length or, since Google usually sends it chunked, against the base64 length of the listed size plus the JSON around it, and stops at 99% until the file is decoded and written; with neither length it reports nothing. The oversized text parts a body fetch resolves still come in one response (`attachment(messageID:attachmentID:)`). Send builds RFC 5322 MIME (multipart/alternative inside multipart/mixed) base64url-encoded into `messages.send`, with `threadId` when replying; messages over 1 MiB of MIME go through the media upload endpoint (`uploadType=multipart`) instead because Gmail caps JSON request bodies. Changes map to `messages.batchModify` label edits.
- **SSGraph**: Microsoft Graph client. Bootstrap = `/me/messages?$orderby=receivedDateTime desc&$select=...` paging, excluding Deleted Items and Junk by parentFolderId. Changes = per-folder `/me/mailFolders/{id}/messages/delta` for inbox, sentitems, drafts, archive, deleteditems, junkemail and every other folder at any depth, found by walking the tree from `/me/mailFolders` (hidden folders left out) through `/childFolders` wherever a folder reports `childFolderCount` > 0, a level at a time down to 16 levels (`GraphProvider.maxFolderDepth`: far deeper than people file mail, it only stops a broken listing that keeps handing back new children from walking for ever, and a folder below it is left to the bootstrap listing and a reconcile), each folder kept once and its children listed once, so a duplicate or a cycle in the listing ends the walk, and a folder that answers 404 when its children are asked for (deleted since its parent was listed) is skipped with them, as the next walk would find. The walk costs the top-level listing plus one listing per folder with children, a request per page of 200 folders, sent one after another, so it is spread over calls and kept in the cursor (`GraphCursor.walk`: the folders found and the listings still to send, with the nextLink of one a step stopped partway through): the call that starts one looks up the system folders and sends the top level's first page, and each call after sends at most 5 listing pages (`GraphProvider.maxWalkPagesPerCall`, about a second; counted in pages, not listings, so a folder holding thousands of others is listed over several calls), so a tree with 60 folders that have children takes twelve polls and no poll, new inbox mail and all, waits for a whole tree. A listing that fails other than with a 404 holds up neither the step nor the poll: a throttle, a refused token, a cancellation or a reset fails the call as its next request would, and anything else (a 500, access denied, a 503 or 504 without Retry-After, a page that does not decode) ends the step with the listing left first in the walk for the next call to try again; after 3 calls (`GraphProvider.maxWalkAttempts`) the walk gives up on that listing and goes on with the rest (`GraphFolderWalk.gaveUp`). A walk starts at bootstrap, which takes its first two steps before the head page (the second only if the first sent no failed listing) and leaves the rest to the polls, and with the daily folder refresh (`GraphCursor.folderRefreshInterval`, counted from the walk's start by the cursor's `foldersResolvedAt`), never on an ordinary poll; the call that starts one keeps the system folder ids it had when a lookup fails. A cursor without the `folderScope` marker was listed two levels deep by an earlier version, so its walk is due on its first poll rather than a day after that listing. A folder the walk finds, at any depth, gets its delta and starts seeding at once (a folder made in Outlook is found by the next walk). One it did not find stays on its delta link, listed in the cursor's `missed`, and is dropped when the next walk misses it too: a walk spread over polls can miss a folder moved meanwhile out of a listing still to come into one already sent, and a deleted folder usually goes sooner, when its delta answers 404. Either way the page names the folder (`ChangesPage.goneFolders`): a folder deleted for good in Outlook takes its mail with it and no delta reports that, so the live lane looks up what the store keeps in it (`storedProviderIDs(accountID:inFolder:)`, then `lookUpMetadata(for:)`) before it saves the cursor, deleting what Graph no longer has and moving what was moved out before the purge. A walk that gave up on a listing drops nothing and adds nothing to `missed`, since it did not look under every folder. A folder found late misses nothing, since its first round lists its whole content. Each delta is seeded without a `$filter` (the only filter message delta accepts, `receivedDateTime ge`, also limits which messages the delta tracks, so reads, moves and deletes of older mail would never be reported); inbox, sentitems and drafts, plus any folder partway through a round on a nextLink, are drained round-robin on every poll until each reaches its deltaLink or about `limit` items are collected; every other folder already on its deltaLink (a quiet folder) waits for a full visit, which starts at most once every 30 s (`GraphCursor.fullVisitInterval`; the cursor keeps when the latest started as `fullVisitAt`, and a cursor without it starts one on its next call) and is spread over calls: each call polls the next quiet folders in id order after the last one the visit polled (`fullVisitAfter`, so a folder added or dropped meanwhile shifts nothing), 2 for every second since the last call (`polledAt`) and never more than 20 (`GraphCursor.quietVisitsPerSecond`, `maxQuietVisitsPerCall`). So a quiet poll is never a heavy page for the live lane (the priority folders, 20 quiet ones, a seed page and a walk step stay under the 34 requests that make one, "Live lane" above) and the quiet folders' cost never holds back the inbox's next poll, however large the tree. At the live lane's 5 s interval a mailbox with 40 folders spends about 1,100 of Outlook's 10,000 requests per 10 minutes per mailbox instead of 4,800, each quiet folder still polled every 30 s, and one with 200 folders about 1,600, each quiet folder polled about every 100 s; a visit of all 200 in one call cost 200 requests, and the live lane held each next poll, the inbox's with it, back about 36 s to pay for that. Polled every 30 s in the background, a visit of more than 20 quiet folders takes more than one poll. Every other folder still in its first round gets one seed page per poll (`maxSeedPagesPerCall` = 1), one folder at a time in folder order, and a seeding folder's nextLink alone does not set `hasMore`, so new inbox mail is never held behind a re-listing of the mailbox. A folder other than the inbox whose delta request fails with anything but a throttle, a refused token, a cancellation or a reset (a 5xx, the network, a 403 access denied, a 400 on its stored link, a page that does not decode) keeps its place and waits for the next call while the others sync, counted in the cursor's `folderFailures` (logged with the status only); a seeding folder that failed yields the seed page to those that did not (`nextSeed`), so one folder whose page keeps failing never holds every later one back from its first round. After 3 calls in a row (`GraphProvider.maxFolderFailures`) it is parked: asked only when a full visit reaches it, seed page and all, and one Graph refused (rather than the service failing) starts a fresh round, since its stored link may be what Graph refuses. Answering clears its count. The inbox failing, or every folder, still fails the call, so the account shows it is not syncing. The first round lists each folder once (a non-priority folder's over several polls, a page per poll), which also repairs anything the offset-paged bootstrap skipped. A removal a delta reports is looked up by id in `$batch` before it counts as a deletion, since a move out of a folder reads the same, and so is a change a delta reports with only what changed (a read flag). Only Graph's answer about the message decides (`GraphProvider+Changes.lookUpReported`): found is an upsert; unknown (404) is gone; refused for that one message (a 400 or 403, a reply that does not decode) takes a removal as gone, which is what Graph's 403 ErrorAccessDenied for a deleted item means, and keeps what the store has for a change; a part or a whole `$batch` the service fails (a 5xx, the network) says nothing about the message, which keeps what the store has and is looked up again on the next call (the cursor's `recheck`, with the calls that failed it) up to 3 calls (`maxLookupCalls`), then is left as stored. The delta links move on meanwhile, so an outage that fails lookups holds no new mail back and deletes nothing that was only moved (a snooze's archive would take the snooze with it); a throttle or a refused token still fails the call. Each page reports the requests its call sent (`requestCount`, tallied by the transport: every attempt, a `$batch` as its parts), which the live lane is charged. The opaque cursor is a resumable record of each folder's place: a JSON map of folder id to deltaLink, plus each folder's in-progress nextLink, the well-known folder ids, when the folder list was last resolved, a folder walk under way, the folders the last walk missed, when the latest full visit started and how far it has got, when the last call ran, the messages to look up again and the folders failing in a row (both absent when none). The backfill listing is the protocol's default over bootstrap, since a Graph page carries its metadata inline. Bodies via `/me/messages/{id}?$select=body,uniqueBody,internetMessageHeaders` with `Prefer: outlook.body-content-type="html"` (the headers are where `List-Unsubscribe` and `List-Unsubscribe-Post` come from: list and delta calls cannot select them, so a Microsoft message learns them with its body) and `/attachments` (Content-IDs selected as `microsoft.graph.fileAttachment/contentId`, since the base attachment type has none). An attachment's raw bytes stream from `/me/messages/{id}/attachments/{id}/$value` into the attachment cache as they arrive (`GraphHTTPClient.download`: the same token retry, request tally and status mapping as every other request), counted against Content-Length or, without one, the listed size (Graph's listed size can run over the file's, so a stated length wins); an attachment with no `$value` (an item or reference attachment: a 404 or another server error) falls back to its base64 `contentBytes` in JSON, in one response. Send via `/me/sendMail` while attachments fit its 4 MB request, otherwise via a draft (`POST /me/messages`); replies via `/me/messages/{id}/createReply` then PATCH then `/send` so Outlook threads them. Draft attachments of 3 MB and more go through `createUploadSession` in 3.125 MiB chunks; a draft whose filling fails is deleted so retries leave no orphans. Changes map to PATCH `isRead`/`flag` and POST `/move`. Batch with `$batch` (20 per call). An apply sends every batch whatever a part of an earlier one answered (a throttle or a refused token stops the rest; a request that failed whole too), sends the parts the service failed again on their own after 1 s and then 2 s (`applyRetryDelays`), and throws what it still owes: the error alone when nothing landed, otherwise `PartialApplyError` naming the messages it did not change, with the gravest error met (refused token, throttle with the longest Retry-After, a failed request, the service, a refusal). 429, and 503 with Retry-After, map to `throttled` with the Retry-After value, and each throttled response is logged once at notice in the "graph" category (status, Graph error code, Retry-After, nothing about the mail); a 502, and a 503 or 504 without Retry-After, is a network error (the service failing for now: the network backoff, "slow to respond", never an operation's give-up), as Gmail's 502, 503 and 504 are, while a 500 stays a server error. `metadata(for:)` leaves out a message Graph will not return on its own as it leaves out an unknown one, so one such hit never fails a server search; `lookUpMetadata(for:)` says which it left out without knowing them gone.
- **SSCore support folders** (`ListSupport/`, `ConversationSupport/`, `ComposeSupport/`, `ShellSupport/`): the pure, testable halves of the app's surfaces (row text and layout, the server row's words and rules, the reader's render payload and shell, reply recipients and drafts, the sync line, undo order, toasts' words, which rail folder takes which dragged rows). `Model/AccountLabels` is the one place an account's monogram, tile letter, name and From title are derived, so every surface shows the same ones.
- **SSDesign**: the Quire design runtime and every component, as a library the app links. See "Design" below.
- **SuperSparrowApp**: `AppDelegate`, `MainWindowController` (NSSplitViewController: account rail, message list, conversation), `MessageListViewController` (NSTableView, fixed rows, manual layout, cached attributed strings; a search ends with the server row, run by its `ServerSearchController`), `ConversationViewController` (warm `WKWebView` pool, `ss-cid` scheme handler, quick reply), `ComposeWindowController`, `KeyboardRouter`, `SettingsWindowController` (SwiftUI), `NewMailNotifier` and `NewMailNotificationResponder`, the Dock badge, and, in debug builds, the Design Gallery (`Design/`, below). The account scope (All Inboxes or one account, chosen in the rail, the title menu or with ⌘0…⌘9) is remembered across launches: the main window saves it in UserDefaults through `AppSettings` whenever it changes (`accountScope`: `unified` or the account id; the demo keeps its own under `accountScope.demo`, so trying the demo never changes the real choice) and restores it at its first read that finds accounts, before the list's first query, so the list never shows All Inboxes first (the tile is scrolled into view only when the rail appears, at the window's final size, so the stack opens as choosing that account there would leave it). A saved account that is gone opens All Inboxes and the saved value is cleared; a demo seeded after its window opens (its first launch, or after its data was wiped) always ends that way, since the seeder gives every account a new id. Removing the scoped account returns to All Inboxes and saves that. It is not a setting and has no UI of its own.
- **Mail links**: `Resources/Info.plist` claims the `mailto` scheme (`CFBundleURLTypes`), so LaunchServices hands SuperSparrow a link clicked in Safari or chosen in Contacts once it is the default mail app. `AppDelegate.application(_:open:)` passes every URL to `MailLinkInbox`, which keeps the mail links and drops anything else; a link that launches the app can arrive before `applicationDidFinishLaunching` has built the main window, so the inbox holds links until there is a main window to open them: `install` hands it each main window it puts on screen (`openMailLinks(in:)`), which has read its accounts by then, and the held links open over it in order. `MailtoLink` (SSCore/ComposeSupport) reads a link per RFC 6068: the address part and the `to`, `cc`, `bcc`, `subject` and `body` fields (names in any case, percent-decoded as UTF-8, a `+` kept as a plus, a malformed escape kept as written, line breaks as `\n`), and ignores every other field. `MainWindowController.openMailLink` opens a new composer (`ComposeWindowController.present(…link:)`) from the account a new message starts from (the scoped account, else the first in rail order), with the link's fields as the window's starting point, so closing it untouched keeps no draft; with no account it brings the welcome screen forward and opens nothing. Nothing is sent or queued until the user sends. Settings › General's Mail links row (`DefaultMailAppModel`) asks and changes the default only through `MailtoDefaultHandling`: in the app LaunchServices (`NSWorkspace.urlForApplication(toOpen:)` off the main thread, `setDefaultApplication(at:toOpenURLsWithScheme:completion:)`, which macOS confirms with the user), in tests a fake, and in snapshots a fixed "not the default" that asks nothing. It asks when the tab appears, when the window reopens on General and when the app comes to the front while General shows, never on a timer.
- **Signatures**: one per account, a local setting in `accounts.signature` (docs/DATA-MODEL.md), kept as the composer's own HTML subset and never read from or sent to the provider as a setting, so it needs no OAuth scope. Settings › Accounts edits it in the detail form (`SignatureField`, wrapping `SignatureEditorView`: the composer's `ComposeTextView` with lists and quotes off, in the Quire field container `QuireTextAreaStyle`), and saves it once editing ends (focus leaving the field, another account chosen, the window resigning key or closing; a composer opening while Settings is key and quitting end editing first through `SettingsWindowController.endEditing`: the main window's `beforeCompose` runs before any composer it opens reads the accounts (⌘N, a mail link, a notification's Reply, whose banner leaves Settings key, the quick-reply hand-off), and quitting ends it before the stores close, since AppKit's will-terminate comes after), through `ComposeSignature.html(from:)`, which is `ComposeBodyNormalizer` then `ComposerHTMLExporter`, so only what the composer sends is kept; `SettingsModel.setSignature` writes the store (`MailStoring.setSignature`) and both windows re-read their accounts, so composers opened afterwards take it (a token's New Message in an open composer re-reads them from the store). The composer applies one rule (`ComposeSignature`, spec §5.20): a new message, reply, forward, mail link or quick-reply hand-off starts with the typed text, one empty line and the From account's signature (read back by `ComposerHTMLImporter` in SSCore, which keeps only that subset), marked with a private attribute (`ss.composer.signature`) that typed text never takes; a From change replaces the marked range as one undoable edit (closing the link popover first, whose range would point at moved text), removes it with its empty line when the new account has none, and adds nothing once the user has deleted it; a reopened draft is left as it was. The signature is ordinary body text, so the existing send pipeline exports it in the HTML and the plain-text alternative, and its marked characters do not count as the user's work when deciding whether a draft is worth keeping (text typed inside it does). A quick reply sent from the bar appends the account's signature as the composer exports it (`QuickReplyComposer.outgoingMessage(signature:)`).
- **Notifications**: `NewMailNotifier` (one per main window) posts a notification per new conversation, or one summary per account past three in 30 s (spec §5.41). A notification for one conversation carries the `newMail` category and, in its user info, the conversation; the summary carries neither. The category (`NewMailNotificationAction`) holds three actions: Archive and Mark as Read, which run in the background, and Reply, which brings the app forward (`.foreground`); Reply opens a composer, not an inline text field. `NewMailNotificationResponder`, owned by the app delegate, registers the category and becomes the center's delegate in `applicationWillFinishLaunching`, because macOS launches the app to deliver an action and hands the response only to a delegate set before launch ends. It reads each response into a `NewMailNotificationResponse` (a click, archive, mark read or reply, with its conversation; a dismissal or an unknown identifier is nothing), brings the app forward for a click and for Reply, and holds responses, as `MailLinkInbox` holds links, until `install` hands it the main window it put on screen (`answerNotifications(in:)`); later responses go to that window at once. `MainWindowController.answer` opens and selects the conversation for a click, as before; applies Archive and Mark as Read through the window's own action path (the same `MailActionRecord` targets as the keys, applied to the store in one call and queued as operations, so they sync), but with no toast and no entry in the undo history, which belongs to the window; and for Reply opens a reply composer to the conversation's latest stored message from its account, as R does. An action on a conversation the store no longer has, one the change would leave as it is, or an account the window does not show (the demo's and the real store are separate) does nothing. The responder reaches the center only through `NotificationCenterRegistering`, since `UNUserNotificationCenter` raises in a process without a bundle; in `swift run` and the tests notifications are off.
- **Unsubscribe**: `List-Unsubscribe` (RFC 2369) and `List-Unsubscribe-Post` (RFC 8058) are captured at sync time and stored on the message as sent (`messages.list_unsubscribe`, `list_unsubscribe_post`, schema v14, docs/DATA-MODEL.md): Gmail from every metadata fetch and the full body fetch, Graph from the body fetch only. Headers never change, so a write that carries none (a Graph listing) keeps the stored pair. Mail stored before v14 has none until fetched again; nothing fetches it back for this. `UnsubscribeMethod` (SSCore/Model, pure) reads the pair as the one way to ask: the angle-bracketed URIs in order, comments and folding white space tolerated, mailto, https and http only; an RFC 8058 one-click request when the post header is exactly `List-Unsubscribe=One-Click` and an https URI is offered, else the first mailto naming exactly one recipient, else the first https (or http) page; a URI with a user name or password in it is skipped. The render payload carries one flag per message (`unsubscribe`), so the reader's shell shows the link beside the sender (spec §5.14) without deciding anything; the More menu's item, Message › Unsubscribe (⇧⌘U, the open conversation's latest message that offers it, read from the reader's messages, so validating it reads no store) and the same item in the rows' and messages' context menu (there only when the open conversation offers it) take the same path. One click, no alert: `MainWindowController.unsubscribe(from:)` computes the conversation's archive as E would (`MailActionRecord`) and calls `MailClient.unsubscribe`, which stores the archive and, for a one-click or mailto method, an `unsubscribe` operation (`MetadataChange.unsubscribe`, carrying the method and URI, no targets) in one transaction (`MailStoring.enqueue(_:)` for several operations). A snoozed conversation (in Later, or a search's result) is archived already, so its snooze ends instead, as E ends it in Later, in the request's transaction (`MailStoring.setSnoozes(_:enqueueing:at:)`): the list's mail never comes back to the Inbox at its time. A page is opened at once with `NSWorkspace`; no engine is involved and only the archive (or the snooze's end) is stored. The toast says what became of the request and offers Undo for the archive (“Unsubscribe sent · Archived”, spec §5.30), or for the snooze's end, which puts the snooze back; its undo group never coalesces (an E in Later after it, named Archive like it, starts a toast of its own), and Undo brings the conversation back while the request stays sent, which the undo's confirmation says (“Undid Archive · Unsubscribe stays sent”). While that toast is up, the same request asked again (⇧⌘U again where the archived row stays listed) does nothing, so it is never queued twice and the toast keeps its Undo; the shell ignores a double-click's second click on the link, which may land on the next conversation's link once the archive has moved the reader on. `OperationRunner` sends unsubscribe operations after the account's other operations, each on its own through `Unsubscriber`: they change no message, so they never wait behind, or hold back, the archive or anything else. The one-click POST runs off the live lane's cycle on a task of its own (`Unsubscriber.detach`), its row written ahead past the request's whole timeout so no later drain sends it twice, so a slow sender's server never holds back a poll; stopping the engine cancels it and leaves the row for the next run (`stopAndWait` waits for it to write its row). The mailto request is the provider's own send and is waited for like any other provider call. The one-click POST (body `List-Unsubscribe=One-Click`, `application/x-www-form-urlencoded`) goes on a session made for the request and invalidated after it: ephemeral, no cookie storage and none sent or accepted, no credential storage (an authentication challenge other than the server's certificate is declined, never answered: a password challenge ends in its 401, a client-certificate request goes on without one, and default handling, which could answer Negotiate with the Mac's Kerberos sign-in, is not used), no cache, 15 s per request and 30 s in all, redirects followed only to https. The mailto request goes through the provider's own send (`MailProvider.send`) from the conversation's account, to the link's one recipient (the mail leaves silently with words the sender chose, so a link naming several recipients is not used and its Cc and Bcc are ignored), its subject or “Unsubscribe”, its body as plain text, with no undo window and outside the outbox's sending count; the provider files it in Sent and the next poll brings it. The outbox's send path is not used because it gives up on a network error (the provider may have delivered), where an unsubscribe waits for the network like any operation. Offline, a dropped connection, the provider's throttle on a mailto send, or a stop (told by the task's own cancellation; a cancelled request otherwise counts as a failure): tried again on the operation backoff, never given up. A 2xx (or a sent mail) confirms it; a 4xx other than 408 and 429, a redirect away from https, or a provider's refusal drops it quietly; a 5xx, the sender's 408 or 429 (its `Retry-After` honoured, up to `SyncTuning.userRetryAfterCap`), a timeout or an unreachable server is tried again until `SyncTuning.maxOperationAttempts`, then dropped quietly, so a sender's server that keeps throttling is not asked for ever. Dropped is deleted, never written as failed, so no row shows a failure and nothing is given back (the request changed nothing locally). A refusal is logged at notice with its status and no URI; the URI, which can identify the user, is logged at debug only. The demo's senders are made up, so the runner sends no POST for a demo account.
- **What the Mac provides**: the composer's body and the Settings signature field (both `ComposeTextView`) and the quick reply turn on spelling as you type and turn off grammar themselves, since a text view built in code does neither (seen on macOS 27.0.1: it starts with continuous spelling off and grammar on), so a new text view where mail is written must set both; text replacement and autocorrection are left to follow the user's own settings, and Writing Tools is offered (`writingToolsBehavior` left at its default, so macOS chooses between its inline and panel forms; all three are TextKit 1 views). Subject and recipients use the window's one field editor, left as AppKit sets it up, which differs from those views (seen on macOS 27.0.1): text replacement and autocorrection follow the user's settings and Services is offered, but spelling is checked only on request (Check Document Now), grammar is on (so that check, and Check Spelling While Typing if the user turns it on there, marks grammar too), smart quotes, dashes and links are off, and Writing Tools is offered in its limited, in-panel form (`.limited`). The four fields share that editor, so a setting changed on it from one (as `TokenInputField.becomeFirstResponder` sets its caret colour) holds in the others. `MainMenu`'s Edit menu carries the text system's Spelling and Grammar, Substitutions, Transformations and Speech submenus; AppKit adds Writing Tools, AutoFill, Start Dictation… and Emoji & Symbols to it as the app finishes launching, finding it by its title and its Cut, Copy and Paste, and `MainMenuBar` passes their fn shortcuts (fn-D, fn-E) through. `NSApp.servicesMenu` is the app menu's Services item. AppKit asks a Services requestor with the legacy pasteboard names (`NSStringPboardType`), so the body, which reads only plain text, lists the string type under both names; with only `.string` no service that returns text was offered in it. The reader's web view offers selected body text to Services, and inside a body WebKit's own text menu stays (the shell's context menu covers only a card's chrome and its chips, spec §5.35). Quick Look previews attachments through `AttachmentPreviewController` (`QLPreviewPanel`'s data source, files written quarantined to a per-session folder).

## Data flow

1. **Add account**: `MailClient.addAccount` → `OAuthFlow` opens the system browser → loopback receives the code → tokens go to Keychain → provider `profile()` → `Account` row → engine starts the account's two lanes.
2. **Head page and cursor first**: an account without a change cursor gets one from its newest page. The live lane fetches `bootstrap(page: nil)` (100 messages, with the cursor the provider captured before listing), saves a `BootstrapState` holding that cursor and no page, upserts the head in one transaction, saves the state again with its next page, then the cursor, and fetches the newest bodies. A crash or a failed write anywhere after the first save leaves a state whose cursor the next launch adopts, so polling covers every head row (even one newer mail has pushed off a later head) and the backfill lists from the top; so does a download the single-loop engine left in progress, except that its backfill resumes at the saved page. The first poll brings in everything since. However large the mailbox, new mail flows from the first poll on (no gap: the cursor predates the listing, and duplicates are idempotent).
3. **Live lane**: replays the outbox, then polls `changes(since:)` until `hasMore == false`, saving the cursor after each page: every 5 s while the app is frontmost and every 30 s otherwise (the schedule runs on the monotonic clock, so setting the Mac's clock back cannot postpone a poll), plus on `syncNow`, activation, waking from sleep and the network coming back. Only Sync Now and Reconnect (`syncNow`, `WakeReason.poll`) try a parked account's token again; the automatic checks (`checkForMail`, `WakeReason.check`) leave it parked, so a refused keychain's prompt never comes back with nobody asking, and the token provider, shared by every account, is never held on that prompt. It then fetches the bodies of the newest 20 messages new to the store or back from Spam (not other stored ones whose labels or folder changed, and not spam), 2 at a time and only as many as its share of the quota pays for, and leaves the rest to the backfill; after a head page (a new account, or a reset) it fetches the newest 20 whatever the share holds. It never waits on the backfill, so a throttled download cannot hold back new mail, archive or star; what it can put off it fits to its own share of the quota ("Quota budget"): after a changes page that said `hasMore` or was heavy (more than a tenth of the share: about ten Gmail messages, or 34 Graph requests), the next page, of the same poll or the next, waits outside the cycle until the share covers another page like it, so a catch-up larger than the share goes on at about a page a minute on Gmail, and so do the polls of a busy mailbox that each bring a heavy page, while the outbox keeps moving. After a light page the next poll's first page goes whatever the share owes (the bodies of an opened conversation count against it), so the steady poll (2 Gmail units) and a few new messages never wait, and nor does Sync Now unless a run or a heavy page came just before it. While a backfill runs, it marks each page's upserts and deletes (`markLiveChanges`) before writing them. A rejected cursor (`resetRequired`) no longer wipes anything: the live lane takes a fresh head page and cursor and only then replaces the old backfill (its state first, with nowhere to resume from, then its marks) with a reconciling one. A reset whose head fails leaves the running backfill as it was, and one whose writes fail leaves a reconcile that lists from the top before it sweeps, never one resumed with half its marks. Only a cycle that polled moves its phase: a user action during a failing poll's backoff runs the outbox alone and leaves "Couldn't sync", "Rate limited" and the retry countdown as they were. Its throttles and failures back off up to 60 s (a provider's Retry-After is honoured up to that cap: a time hours away is more often a skewed clock than advice); a throttle on any of its requests (a head or changes page, the outbox, a body it fetches) also pauses the backfill, which it never waits on ("Quota budget"); and a refused token or keychain parks both lanes until Sign in or Sync Now.
4. **Backfill lane**: downloads the rest behind the live lane, paced by the account's quota budget. One listing page at a time from the saved page token (Gmail: ids only, then metadata ten at a time for the ids the store lacks, each chunk written as it arrives; Graph: metadata inline), written with `writeBackfillMessages`, which skips whatever the live lane wrote or deleted meanwhile, so a page fetched before a live change can neither undo it nor bring back a deleted message (docs/DATA-MODEL.md, "Backfill marks"). The state is saved after every page, so a quit resumes there, and a stored page token the provider rejects restarts the listing from the top. Each page is followed by one paced body batch (inbox first, newest first), a page that failed too unless the failure is one the batch would meet (a throttle, a refused token or keychain, the network, a park), so a page that keeps failing never stops the bodies; once the listing completes, the lane fetches the remaining bodies, then sleeps until woken or for 5 minutes. Every body batch is followed by one local batch of design facts for bodies stored before v3. At launch the lane waits for the live lane's first cycle, so a token or keychain prompt is asked for once, and it looks at the park before every request, so a turn under way stops once the account is parked. A reconciling backfill also refreshes stored rows and records every id it lists; when complete it removes the stored messages the provider no longer listed, except those a live operation targets, and those only if the provider, asked just before (`lookUpMetadata(for:)`), no longer has them: their deletion sat in the expired history, so no poll would report it. One the provider will not return on its own (Graph's 403 for one message, a part the service fails) is kept like any other target rather than failing the reconcile on every retry. A throttle pauses this lane, and so does a throttle on anything that spends the live share ("Quota budget"): no request of this lane goes out until the pause ends, one already waiting for its units included, and a throttle on one fetch of a body batch stops the fetches of that batch that have not gone out, so the batch reports it while the pause runs. The pause shows as `AccountSyncStatus.backfillPausedUntil` from the moment a request of this lane meets it until that request goes out, so a pause after the download has finished shows nowhere. Its errors never change the live phase. A failure backoff ignores wakes, except a replaced backfill and bodies of new mail the live lane hands over after a poll that went through (the network is back).
5. **User action**: UI calls `MailClient.perform` (from a key, a menu, a reader button, or rows dropped on a rail folder, which all take the same path in `MainWindowController`) → `store.enqueue(operation)` applies the change to the targets and inserts the operation in one transaction → observations fire → `OperationRunner` replays pending operations in order per account with exponential backoff, a call per 50 targets (`SyncTuning.maxApplyTargets`); a slice the provider refused in part or whole does not keep the later slices from going out (only a throttle, a refused token, the network or a cancellation does), and an operation the provider took in part keeps only the targets still owed (`PartialApplyError`), so a retry sends those alone and a give-up puts back only those; `confirmed` operations are deleted; `uncertain` ones (timeouts) are left for a poll to settle once it has reported every target and their last attempt is 10 minutes old (docs/DATA-MODEL.md, "Confirmed operations"), and retried meanwhile. An attempt counts towards the give-up (`SyncTuning.maxOperationAttempts`) only when the provider answered it: on the network or a throttle the count stops where the backoff reaches its cap, so an hour and a half offline never leaves the first server error after it to give the change up; a token that could not be had (the token endpoint failing) is retried the same way and never given up, and a keychain the user refuses parks the account at once, before the poll asks the keychain again, without counting the attempt. An invitation's answer is never settled by a poll, which does not report it, so it retries until it is confirmed or given up. Answering an invitation is the same path (`MailClient.answerInvitation` builds the operation from the stored invitation), with one difference: before any replay the runner asks the provider, without a request, whether the change needs a permission the account has not granted (`MailProvider.missingPermission(for:)`, from the token's scopes); such an operation is not tried, spends no attempt, holds back only later operations of its own kind on its messages (an archive, trash or read change of the same message still goes, since the wait lasts until the user reconnects and an answer never moves the message), and the account reports the permission (`AccountSyncStatus.permissionsNeeded`) until a drain finds it can go. Before that, every drain drops an answer a newer answer on the same message replaces, whether it waits for the permission, sits in a backoff or may have landed, so the organizer hears the latest answer and never each one on the way; a `notFound` from an answer gives it up at once. An unsubscribe (`MailClient.unsubscribe`) stores the conversation's archive (or the end of its snooze) and its request together, and the runner sends the request after the account's other operations ("Unsubscribe" above).
6. **Pending operations win**: when a poll upserts provider state for a message that has a pending or in-flight operation, the store re-applies the pending changes on top of the provider state so an archived thread cannot pop back into the inbox before the provider catches up.
7. **Send**: `MailClient.send` stores a `PendingSend` with `sendAfter = now + undoWindow` and wakes `SendRunner`, which sends it after the window; the sent message appears via the next poll (Gmail returns `threadId`, Graph threads by `conversationId`). The runner keeps no tick: it sleeps until the earliest held send falls due, or until woken by a send being queued or by `checkForMail` (the Mac waking, the app coming to the front, the network returning), so a send whose window ended while the Mac slept goes on waking. A held send is timed on the continuous clock from the moment it is queued (or throttled), however late the runner first reads it (it may be delivering another send), so setting the Mac's clock neither cuts an undo window short nor holds a send past it, and its timer allows a tenth of a second of slack rather than the system's tenth of the wait. A send a previous run left has only its stored wall-clock time, which may have been set since, so it is held no longer than the runner ever holds one itself (60 s, a throttle's longest retry; the undo windows are shorter). With nothing held, the runner looks at the outbox only at the background poll interval (30 s), for a send stored without a wake, and the sync line's sending count observes the outbox (`MailStoring.observePendingSends`) rather than polling it, with a one-shot timer at the end of the next held send's window (the runner delivers one send at a time, so one whose window ends while another uploads is claimed, a write, only after that upload), so sending keeps no timer faster than the poll in an idle app (the other timers are under "Performance budgets"). Stopping the engine (quitting, leaving the demo) ends the runner between deliveries: a send not yet handed to the provider, one that fell due while another uploaded, stays held for the next launch rather than going to the provider under a cancelled request and failing. Claiming a send and Undo take one lock, so a message is never both cancelled and sent; Undo needs no wake (the runner finds nothing at the old time). A throttled send goes back in the outbox for the provider's retry time (the backoff schedule without one), capped at 60 s as a user action's is, and is retried then; so does one that failed before any request left this Mac (`ProviderError.neverLeftThisMac`: no network, no route or no name for the host, or a token refresh that could not connect, as at a wake before Wi-Fi is back), on the backoff schedule, since nothing reached the provider; after any other failure it is marked failed and never retried, since the provider may have delivered it. The runner claims one send at a time (marks it `sending`) and reads the outbox again after each delivery, so a crash or a force quit leaves in doubt ("interrupted while sending; check Sent") only the send actually handed to the provider, never one that fell due beside it.

8. **Send and Archive** (spec §5.23). What Send, ⌘↩ and Message › Send do is a preference (`AppSettings.sendAction`, `SendAction` in SSCore: Send and Archive by default, or Send), read and changed through `SendActionPreference`, which the main window points at its settings; it is not in Settings: the drop-down beside the composer's and the quick reply's Send (`SendActionMenu`, a `QuireIconButton` menu button) sets it, and a change is posted so every open composer and the quick reply retitle their Send at once (tooltip and VoiceOver name; the label stays “Send”, and a new message, which answers nothing, says Send). ⇧⌘↩ (the composer's content view and the quick reply's text view take it before the menu, as they take ⌘↩) and Message › Send and Archive always archive. Archiving happens right after `MailClient.send` has queued the message, the moment the undo window starts: the composer or the reader asks `SendArchive.archiver`, the main window (`MainWindowController.archiveConversation(answering:client:)`, only for its own engine and accounts), to archive the conversation of the message answered as E would (`MailActionRecord`, the messages in the Inbox, applied and queued through `MailClient.perform`; the return mark of a conversation back from Later kept for the undo); a snoozed conversation is archived already, so its snooze ends instead (`setSnoozes`, as E in Later). Nothing joins the window's undo history and no toast shows: the `SendArchive` it hands back travels with the send (the undo-send panel, the quick reply's `QuickSend`, and the panel a hidden bar's countdown moves to), whose Undo cancels the send and then reverts it with the inverse steps (or puts the snooze back) and reselects the conversation if the archive had taken it off the screen, exactly as Z after E; Edit › Undo reads “Undo Send and Archive” meanwhile. A send that leaves, an Undo that comes too late or a send that fails after its window leave the archive as it is. The two writes are separate transactions (the outbox's `pending_sends` row, then the archive's operation), a few microseconds apart on the main thread.

9. **Later** (spec §5.45, docs/DATA-MODEL.md "Snoozes"). L on the selection pops the Later menu (`LaterMenu`, the presets of `LaterPreset` worked out in the local calendar, then Pick a Date…, `LaterDatePicker`, a system alert sheet with a calendar and a time field), hung from the selected row or, with focus in the reader, from its header; Message › Later… and the row's context menu carry the same items. A choice calls `MailClient.setSnoozes` with the archive step for the messages in the Inbox (`MailActionRecord`, as E computes them), for the conversations a snooze can hold once archived (`Snooze.canHold`, the store's own rule: one whose mail from others is all in the Trash, as # leaves it on Microsoft with the user's reply still in Sent Items, has nothing to bring back, so L beeps for it as E does when it changes nothing, and a selection snoozes the rest): `store.setSnoozes` applies and queues the archive and writes the snoozes in one transaction, so the rows leave the Inbox and the selection moves on as after E; the toast says when they come back (“Snoozed until Tue 09:00”, or “Until …” where `ToastPresenter.fits` finds the sentence would be cut off), and its undo calls `setSnoozes` again with the times they had before (none, or the old time of a reschedule) and archive's inverse. An Archive, Move to Trash or snooze of a conversation back from Later records its `returnedAt` (`MailActionRecord.returnedAt`, read from the row), and the undo passes it with the inverse steps (`Snooze.Change.returnedAt`), so the row returns under Today with its Back tag as every undo puts a row back where it was. Only the timer lives on this Mac: `SnoozeRunner` (one per engine) returns what is due in one transaction per batch of 200 (`returnDueSnoozes`: the snooze goes, the ordinary move-to-inbox and mark-latest-unread operations are queued a millisecond apart for the mail the snooze put away (`MailActionRecord.returnTargets`), never a message in the Trash or Spam and on Microsoft not the user's own copies in Sent Items and Drafts, so the phone and the web see the same state, and the conversation is marked `returned_at`), then waits once, on the continuous clock, until the soonest snooze falls due; with nothing snoozed it keeps no timer. A due snooze first waits for its account's live lane to finish a check that began at or after its time: the lane reports each full cycle's start and, when its poll caught up, its end (`liveCheckStarted`, `liveCheckCaughtUp`, stamped on the runner's clock behind a lock so they land in order), and the runner asks the lane to check (`.check`, which leaves an account parked for sign-in parked) when it starts waiting. The outbox replays before each poll, so a return queued from what the store held when the app quit or the Mac slept would mark an old message unread on every device and tag a conversation whose overnight reply (or move to the Inbox on the phone) had not been seen yet; after the check, that mail is in the store and has ended the snooze by the rules below. The check usually lands within a second or two. An account that cannot check (offline, signed out, failing) is waited on for a minute of awake time at most (`SnoozeRunner.checkWait`, measured on `SendClock.awake`, which stops while the Mac sleeps, so a wait under way when the lid closes does not run out at wake), and then returns without it: offline, a reply that came meanwhile can still meet a return already queued. It is woken by `setSnoozes`, by `checkForMail` (the Mac waking, the app coming to the front, the network returning), by the wall clock being set (`NSSystemClockDidChange`, which a continuous wait cannot see) and by the check it waits for; it runs at launch, so a time missed while the app was closed returns then, and a time passed while the Mac slept returns at wake, each once its account has checked. No notification is posted for a return (`NewMailNotifier` skips rows with `returnedAt`). The Inbox sorts, pages and groups by `COALESCE(returned_at, latest_date_ms)` (the `conversations_inbox` index is built on it), so mail that comes back lands under Today, with a Back tag on its row while unread. The store ends a snooze on its own when its conversation is back in the Inbox (⇧I, a drop on Inbox, another device, new mail), in the Trash (on Microsoft, everything but the user's own copies, which # leaves in Sent Items and Drafts) or gone, and when mail that is not the user's own arrives after it was snoozed; a removed account takes its snoozes. The window observes the snoozes (`MailStoring.observeSnoozes`): the rail shows the Later tile below Inbox, the title menu and the View menu list Later, and G L opens it only while something in the scope is snoozed; the Later view lists them soonest first, rows reading "Back Tue 09:00". There L moves the time, E ends the snooze and leaves the mail archived (presses within the window coalesce, `MailActionUndoHistory.coalesceExternal`), Unsubscribe sends its request and ends the snooze the same way, in one transaction, under a toast no E joins ("Unsubscribe" above), ⇧I moves it back now (the same messages its time would, `MailActionRecord.returnTargets`, also for a drop on Inbox or ⇧I on a snoozed conversation found elsewhere) and # trashes it, each undoable with the snooze restored; when the last snooze in view ends the window returns to the Inbox, keeping a search typed there (it lists All Mail, or the view an `in:` term picks, whatever the view on screen; "Search"). Later is read whole, never paged (`ShellQuery.laterLimit`), and nothing in the search grammar picks it, so a search never reads it. An undo of a step taken in Later brings Later back only when the window left it because it emptied and the user has not since picked a view or a scope or typed a search (`leftLaterAsItEmptied`); otherwise it selects the restored rows where the user is, as every undo does.

## Quota budget

Each account has one `QuotaBudget`, a token bucket in the provider's own units (`ProviderQuota`). Gmail allows 6,000 units per user per minute: `messages.list` costs 5, `messages.get` 20 with metadata and 60 in full, `messages.attachments.get` 5, `history.list` 2. Outlook allows 10,000 requests per 10 minutes per mailbox, so 1,000 a minute, and Graph counts each request inside a `$batch` on its own: metadata fetched by id costs 1 request per message, a listing page with metadata inline 1, a body 2 (the message and its attachments), an attachment's bytes 1 (its `$value`). The backfill lane may spend two-thirds of the allowance, takes its units before every request and keeps at most 2 in flight; the live lane never waits for the backfill's units and records an estimate of its spend in the same bucket: each head page (plus, on Gmail, 20 units of metadata per message; Graph's carries it inline), each changes page, each body it fetches, each message the user opens and each attachment the attachment cache downloads (5 Gmail units, 1 Graph request, recorded before the request goes out; a file already cached costs nothing), since a file the user opens, saves or sees inline is as much the user's action as an opened message and never waits. A search of the server is recorded the same way, before each request: its listing (5 Gmail units for `messages.list`, 1 Graph request for `$search`) and the metadata of each hit the store lacks (20 Gmail units, 1 Graph request apiece), at most 1,005 Gmail units or 51 Graph requests per account for its 50 hits ("Server search"). A Gmail changes page is the call plus 20 units per message; a Graph one is every request the call reports it sent (`ChangesPage.requestCount`): a delta GET per folder it visits, a folder walk step's lookups and listings, and a `$batch` part per removal it looks up, three on a quiet poll, about thirteen while a full visit goes on and over a hundred on a page of removals. A Graph head page is likewise every request its call reports (`BootstrapPage.requestCount`): the system folder lookups, the folder walk's first steps and the page. The backfill's listing from the top takes one page's units before it goes out and, when the call reports more (Graph's runs the same lookups and steps), the rest after (`QuotaBudget.recordBackfill`), so its next request waits for them. The estimate leaves out the outbox and sends. The third left over is headroom for that and for the live lane's own spend (a poll every 5 s, a head page of about 2,005 Gmail units, the newest bodies), so new mail never queues behind older mail and a busy live lane slows the backfill, never the reverse. A throttle on the backfill halves its rate and pauses it until the provider's retry time, or 15 s doubling to 10 minutes (the doubling starts over once a backfill request goes through, or once ten quiet minutes have passed since the last pause ended, so throttles hours apart never add up). So does a throttle on anything that spends the live share (a head or changes page, the outbox, a body the live lane prefetches or the user opens, an attachment download, a search of the server: `QuotaBudget.liveThrottled`), since a backfill that went on spending the same per-user quota would keep the provider refusing new mail. A throttle that lands while a pause runs, from either lane, is the same event (a burst refuses the requests in flight on both): it can lengthen the pause to its own retry time but never halves the rate or doubles the pause again. The live lane never waits on the pause and keeps its own backoff; the unmetered demo pauses nothing. Every quiet minute wins back a tenth of the rate. The live lane's spend also comes out of a share of its own, the third the backfill leaves (2,000 Gmail units a minute), refilling at that rate, holding a minute of it and owing a minute, or all of a single cost beyond that (so a Graph page of a thousand requests is paced by what it cost, not by a minute's worth): nothing waits on it, but the live lane reads it before what it can put off, the next page after a run or heavy changes page and prefetching the bodies a poll brought, so its own burst stays within the provider's limit as well. A head page's newest 20 bodies do not wait for it: on Gmail the head alone (2,005 units) spends the whole share, and Gmail took about 5,000 units within 12 s without refusing, so the head and 20 bodies (3,205) stay inside what it accepts. Gmail refuses a few thousand units spent in a few seconds well before a minute's 6,000 (two pages of 137 and 56 changes, 20 bodies and an opened conversation's attachments did it), so a changes page is 100 messages, about 2,000 units, the whole share. The demo's made-up mailbox is unmetered.

## Storage bounds

Settings › General › Keep mail on this Mac (Everything, the default; 1 year; 3 months) bounds what the store keeps whole, with the space the mailbox takes beside it. `MailEngine.setMailRetention` holds the window in `KeepMailState`, and each `AppEnvironment` keeps it on the setting (`follow`, from before the engine starts); `StorageSweeper`, one actor per engine, does the work. It keeps no timer. Work comes from three moments only: once per launch, after the first live cycle of any account, whatever its outcome (the work is local, and offline it is as useful); when a backfill ends, meaning the backfill lane goes idle after listing pages or after at least a batch (50) of paced bodies, since the few bodies of new mail the live lane hands over are not a backfill; and when the window narrows while the engine runs. Widening it, back to Everything included, evicts nothing more and fetches nothing back: those bodies return as their messages are opened. A sweep reads the window as each batch looks for candidates and again inside its write, so even the batch under way when the user widens the window evicts only to the new cutoff, and nothing for Everything, where the sweep stops.

- **Eviction.** A message received before the window keeps its row, `bodies.plain_text`, its attachment list, its design facts and its full-text row; its `html`, `text` and `rendered_html` are cleared and `bodies.evicted` is set (docs/DATA-MODEL.md). The list, snippets and search read none of the cleared columns, so they are unchanged. An evicted body keeps its row and `messages.has_body`, so `messageIDsMissingBodies` never offers it to either lane, while `body(for:)` answers nil, so opening the message fetches it at once through `MailClient.ensureBody`, the path the reader already takes for mail the backfill has not reached (the skeleton while it loads, the offline preview without a network); the save writes it whole and clears the mark. Bodies the user has in front of them stay whole until a later launch: `KeepMailState` keeps a set of them for the run, filled by `ensureBody` before it fetches and by the reader, which passes every message it renders (the conversation on screen and the neighbours it pre-renders, with a stored body or without) to `MailClient.keepBodies(of:)` before it reads any body. Every sweep of the run leaves them out, and each batch reads the set again inside its write, so a clean-up does not take the body from under a conversation on screen, a backfill ending just after the user opened old mail does not evict it again, and an old message costs one fetch per launch at most. A page can still read a body in the instant before a batch's write commits (a reader sees the last commit); the chips, Save Attachments…, Quick Look and the scheme handlers read the attachment list apart from the body (`MailStoring.attachments(of:)`), and an eviction keeps it, so they still find the files, and opening the message again fetches the body. A message shown without a body is kept too, so the backfill fetching it stores it whole and the conversation's next refresh shows it, and one that joins the open conversation without a body (an older message the backfill lists) is fetched at once, as it would be had it been there when the conversation opened. The set sits behind a lock, not on the sweeper's actor, so marking a message never waits behind a sweep step. Drafts (the drafts role), messages a live (pending, in-flight or uncertain) operation targets, and the outbox (`pending_sends`, a table of its own) are never touched. A sweep runs on the sweeper's actor in batches of 200 (`SyncTuning.evictionBatchSize`): each batch reads its candidates on a reader, so a sweep with nothing to do never takes the writer, then evicts them in one write transaction that checks every rule again, so a user action written meanwhile waits for one batch at most. A batch starts at the date the previous one reached (inclusive, so messages sharing that date are looked at again): `evicted` is only checked once a row has been read through `messages_by_date`, so restarting from the oldest message would walk past every body earlier batches evicted, and a first sweep of a 300,000-message mailbox would read for a quarter of an hour instead of about 20 seconds. Stopping the engine stops a sweep between batches. Three other paths fetch an evicted body back, as they already did for mail the backfill had not reached: the reader's pre-render of the conversations next to the selection (through `ensureBody`, so those are kept for the run too); the live lane's prefetch of a message leaving Spam; and the newest 20 bodies of the head page a reset takes after a rejected cursor (`body(for:)` answers nil for an evicted body as for a missing one), which in a quiet account can all lie outside the window. A later sweep evicts the last two again; a reset is rare, so that costs at most 20 fetches per reset.
- **The backfill stores old mail already evicted.** A body the paced path (the backfill lane) fetches for a message received before the window is saved in the evicted form in the same transaction (`MailStoring.saveBody(_:for:evictingIfReceivedBefore:)`, under the sweep's rules), so its source and rendered HTML are never written and a large mailbox's first backfill never takes the full size on disk, which a file an earlier build created could never give back. The window and the kept set are read just before the body is saved, so a message someone asked for before then (`ensureBody` marks it before joining the fetch) is stored whole. One asked for while that save waits for the writer, or after it but before the fetch is done, joins a fetch that has already chosen the evicted form: `Hydrator.ensureBody` then finds no body in the store and saves the one it was handed whole, since the reader reads it back from the store and would otherwise stay on its skeleton with nothing left to fetch it. The live path (new mail, a message leaving Spam, a reset's head page) and `ensureBody` store whole. The sweeps remain for windows that narrow later and for mail fetched whole.
- **Attachment cache.** At most 1 GB on disk (`AttachmentCache.capacityBytes`, as Finder counts), the least recently used going first, by modification date, which the cache sets to now whenever it serves a file (access times are not kept reliably on every volume). It is measured and trimmed when the engine starts, off the main thread, and after a download once the running total passes the cap, down to nine tenths of it: a trim walks the whole folder on the cache's actor, where cached images wait, so a full cache walks it once per 100 MB of downloads, not for every download. It never deletes a file under `.partial` (a download being written), one a download in flight will read back, or the file just downloaded, and it leaves the folder a download in flight will rename its file into even when that folder's last cached file goes. Quick Look previews copies in a temporary folder of its own, so no preview holds a cache file open.
- **Maintenance** (`MailStoreMaintenance`, the SQLite store). `PRAGMA optimize` when an environment shuts down: quitting comes through `AppDelegate.prepareToQuit` to `AppEnvironment.shutdown`, which runs it after the engine's last write and before the store closes. An FTS5 optimize when a backfill ends, as 'merge' steps of 64 pages (about 256 KB), each its own transaction (`MailStoreMaintenance.mergeFullTextIndex`): the first with a negative count, which starts a merge of every b-tree, the rest positive, which carry it on even while live writes add b-trees, until a step changes fewer than two rows. FTS5's own one-statement 'optimize' would hold the writer for the whole index. The steps rewrite the whole index (about 300 steps and a second for a 300,000-message mailbox), so the sweeper takes one step per turn of its actor: stopping the engine waits for one step, not the merge, and a merge stopped halfway starts over at the next backfill's end. Incremental vacuum steps after each sweep, at the same moments: `PRAGMA incremental_vacuum(256)` (1 MiB), at most 1,024 steps per moment, only on a file whose `auto_vacuum` is INCREMENTAL. New files are created that way (docs/DATA-MODEL.md, "The file"). A file an earlier build created keeps NONE, because switching takes a full VACUUM, which the app never runs (it needs twice the disk and holds the writer throughout). Such a file stops growing while SQLite reuses the pages an eviction frees, but it does not shrink. A later release could compact it with `VACUUM INTO` a new file at a quiet launch, then swap the files.
- **The size in Settings.** The database file with its WAL and shared-memory files, less the pages SQLite keeps free inside the file for reuse (`freelist_count` × `page_size`, read on a read-only connection of its own), plus everything under the attachment cache, as allocated on disk (`MailboxFootprint`). The free pages are left out because a file from before v10 never gives space back without a full VACUUM, which the app never runs: counting them, the number would never go down after a clean-up. Measured on a background task when the General tab appears or the window reopens on it, and after the engine reports a sweep or a trim (`MailEngine.observeStorageChanges`) while the window is open. Never on a timer.

Why it matters: at about 15.6 KB a body, a mailbox of 41,000 messages reaches about 700 MB once every body is in, and one of 300,000 about 5 GB. The plain text and the full-text index are a small part of that (17 MiB of index for the 41,000-message mailbox), so a short window keeps search whole at a fraction of the size, from the first backfill on, since the backfill stores what lies outside the window already evicted.

## Search

The search field is the only search UI: no chips, no suggestions, no syntax colouring. The cheat sheet has one line listing the operators (docs/DESIGN-LANGUAGE.md §5.32), and the empty states are the ones words already had (§5.9), whose offer to search the server ("Server search") takes operators as it takes words.

- **Parsing** (`ShellQuery`, pure, SSCore): the field's text, 120 ms after the last keystroke, becomes a `SearchQuery` (`SearchQuery(parsing:timeZone:)`, `ShellSupport/SearchGrammar.swift`): the text as typed, trimmed, and its `SearchTerm`s in order. Words; `"quoted phrases"`; `from:`, `to:` (To, Cc and Bcc), `subject:`; `is:unread`, `is:read`, `is:starred`, `has:attachment`; `before:` and `after:` with a day as YYYY-MM-DD or YYYY/MM/DD (Gregorian, local midnight in the Mac's time zone: `after:` is on or after the day, `before:` before it); `in:inbox`, `in:sent`, `in:drafts`, `in:trash`, `in:all` (the views); and a leading minus on any of them. Names and keywords ignore case, values may be quoted, terms combine with AND. Nothing is an error: an unknown operator or a value its operator does not take is a word (`label:work`, `before:yesterday`). The last term typed, while unquoted or its quote open, is a prefix (words as before, and `from:nakam`); a negated term never is, so typing `-b`, `-be`, `-ben` never leaves out every word starting with b. A last operator whose value is the start of one it takes (`is:un`, `before:2026-0`) adds nothing until finished, so the list does not flash results for the letters. `ShellQuery.make` puts the parsed search on `ConversationQuery.search` and picks the view: the first `in:` that is not negated, or All Mail; the view on screen does not apply while searching, Later included (there is no `in:later`: a search typed in Later looks through All Mail like any other), the account scope does. `SearchQuery.text` is what a provider's own search gets ("Server search"); the terms are what the stores match.
- **What matches.** Words, phrases, `from:`, `to:` and `subject:` are full-text terms: a conversation is a result when one of its messages matches every positive one and no negated one, which is how Gmail's `q` and Graph's `$search` read the same text, so a search of the server ("Server search") agrees with the local one. `is:`, `has:`, `before:`, `after:` and `in:` test the conversation's summary row, what the row shows: its unread dot (`unread_count`), star, paperclip, date (`latest_date_ms`, the latest message, never the Inbox's return time), and the view predicates (`in:` terms beyond the first narrow it, `-in:inbox` leaves the inbox out); negated, they keep the rows they do not describe.
- **SQLite** (`ConversationTable`, `FullTextIndex`): the full-text terms become one FTS5 MATCH expression, each term a quoted phrase (so FTS5 syntax typed in the field stays words) with a column filter for `from:` (`sender`), `to:` (`recipients`) and `subject:`: `(positive AND …) NOT (negated OR …)`, or, with only negated terms, the negated ones with the match inverted (FTS5's NOT needs something on its left). The matching messages become conversation keys in one scan of the covering index `messages_by_conversation`, testing each rowid against the set the index matched (`+m.rowid IN (SELECT rowid FROM message_fts WHERE …)`, or NOT IN), so DISTINCT streams over keys already grouped; joining every hit to its table row and sorting the string keys cost 47 ms instead of 27 for a word in 73% of the 100,000-message fixture. The keys join the summary rows, and the operators are predicates on them next to the view's. What a search of the server found (`ConversationQuery.serverMatches`) is a second test in the same scan, on the conversation key (`OR (m.account_id, m.conversation_provider_id) IN (VALUES …)`), so it joins the hits with the same plan, order and paging, and the operators and the view narrow it alike. `sender` and `recipients` are full-text columns (v12, docs/DATA-MODEL.md) because the address JSON has no index that answers in 50 ms.
- **InMemoryMailStore** answers the same way (`FullTextMatcher`: the four columns, phrases and the prefix), held to it by the contract tests. Words split where unicode61 splits them, by Unicode scalar: its word characters are the letters, digits and private-use characters of SQLite's Unicode 6.1 tables, plus any code point 6.1 had not assigned, so Ⓐ and 🅻 are symbols, the Apple logo and 🥳 belong to their words, and a term with none of them (`Ⓐ`, `@`) adds nothing in both stores rather than an FTS5 phrase with no words, which would match no message. `SearchGrammar.isIndexable` asks the same question. Folding is Foundation's, which agrees with `remove_diacritics 2` for Latin letters but also drops Greek and Cyrillic accents that unicode61 keeps.
- **The open conversation.** Opening a result reads it after 500 ms (the reader's mark-read), which in an `is:unread` search would take the row out from under the reader and hand the selection to the next result, read in turn, until the list had read itself empty. So the list passes the lead, once it has rested 150 ms, as `ConversationQuery.openConversationID` while the search has an `is:unread` or `is:read` term (and only then): read state never takes that conversation out, everything else still does, and the one kept before leaves once another is kept. The list re-observes keeping its pages and selection. Apple Mail keeps the selected message in its Unread filter the same way.
- **Actions on results.** While searching, keys, menus, rail drops and the reader treat the results as rows of the view searched (`MainWindowController.listView`, the list query's view), not of the rail's: `in:trash` results restore with ⇧I and # leaves them be, as in the Trash (so the Trash folder refuses them and takes a plain search's results even with the rail on the Trash), and in a plain search (All Mail) Move to Inbox is offered whichever view is on screen. Later's rules follow the same view: L (`canSnoozeSelection`) refuses `in:trash` and `in:drafts` results and takes a plain search's typed from the Trash or Drafts, and E, ⇧I and # in a search typed in Later act as in All Mail, not as Later's own (E ending a snooze). An action toasts when it takes a row out of the list (§4.13): `MailActionCopy.wantsToast` applies the rules of the view searched and of the search's terms (archiving in an `in:inbox` search, unstarring in an `is:starred` one); read state never takes the open row out, so it never toasts.
- **Budget**: the 50 ms keystroke, with every operator alone and all of them together, on the 100,000-message fixture (`SearchOperatorPerformanceTests`, `SS_PERF=1`): 1.5 to 7.7 ms for the row operators, phrases and names, 18 to 32 ms for a term in most messages (`to:owner`, `-invoice`, `budget -spreadsheet`), 12 ms for every operator at once, 15 to 32 ms with 50 conversations a search of the server found ("Server search"), whose keys are tested on every message of the scan the full-text match leaves out. A one-letter word prefix (`t`) takes about 85 ms, as it did before operators (106 ms with the old join): FTS5 merges every token that starts with the letter, and a prefix index would cost index size.

## Server search

The list's search reads only the store, so during the first download of a large mailbox it cannot find what has not arrived yet. When a search's local results have all been listed (no older page left to load), the list ends with a row that offers the server (spec §5.10): “Search Gmail for more”, “Search Outlook for more” for a Microsoft account, “Search all accounts for more” in All Inboxes with several accounts; a search with no local results offers it in its empty state (§5.9). ↩ in the search field, Edit › Search Gmail for More (no key equivalent), a click on the row's link, ↩ on the link once Tab has reached it, or the empty state's link runs it; ↩ in the field then gives the keyboard to the list, and while the field has the keyboard the row and the empty state show a “↩” keycap. The UI never calls a provider: `MessageListViewController`'s `ServerSearchController` calls `MailClient.searchServer(for:accountIDs:)` on a task and keeps the row's state; nothing waits for it and the local results stay on screen as they were.

- **The engine** (`ServerSearcher`, through `MailEngine.searchServer`) searches the accounts in scope two at a time (`SyncTuning.serverSearchConcurrency`), each with one `MailProvider.search(text, limit: 50)` (`serverSearchLimit`): the field's text as typed, trimmed (`SearchQuery.text`, operators and all), under the provider's own rules (Gmail's `q`, so its own `from:`, `is:unread` and `has:attachment` work and Spam and Trash are left out by Gmail's default; Graph's `$search` over every folder, KQL-like, as one quoted phrase with its quotes and backslashes escaped), never the local parser's terms; a '+' goes as `%2B`, since both providers read a bare one as a space. The hits the store already holds, and those the live lane wrote or deleted while a backfill runs (`backfillSkippableIDs`), need no request: the stored ones join the result as they are, and nothing about them changes. Metadata for the rest comes from `metadata(for:)` (Gmail's metadata batch of ten parts, as the backfill fetches it; Graph's `$batch` of twenty), and the hits not in Trash or Spam are written in one transaction per account through `writeBackfillMessages`, which drops in that same transaction anything stored or marked meanwhile (docs/DATA-MODEL.md, "Backfill marks"). So a hit is an ordinary row: the full-text index has its subject, people and snippet at once (a message is indexed by its snippet until its body is stored, v13), so a later search of those words finds it again with no server matches named; the backfill and the live lane treat it like any other message, and a reconcile keeps it if the provider still has it. No body is fetched: opening a found message fetches it through `MailClient.ensureBody`, the reader's path for mail the backfill has not reached, and the backfill fetches the rest of the bodies in its turn. The result names the conversations of every hit the store holds now and the accounts whose search failed (offline, throttled, signed out); a failed account never fails the others, and its error is never an alert. Cancelling the task (new words, another scope) stops the search at its next request and starts no other account; metadata already fetched is still written, since its quota is spent. Each search is a `sync.serverSearch` signpost interval.
- **Quota.** Every request is recorded as live spend before it goes out, and a throttle on one pauses the backfill (`QuotaBudget.liveThrottled`), as for any request that spends the live share ("Quota budget").
- **The list.** The found conversations join the list's query as `ConversationQuery.serverMatches`: the store lists them with the full-text hits whatever their stored text says (a body not downloaded holds the words the server matched), in date order. They stand in for the full-text terms only (words, phrases, `from:`, `to:`, `subject:`), which the server's own rules decided; everything this Mac tests on the row still narrows them: the search's `is:`, `has:`, `before:`, `after:` and `in:` terms ("Search"), the view (Trash stays out) and the account scope, so `is:unread lisbon` lists only the unread finds. A search with no full-text terms (`is:starred` alone) has no match for them to stand in for: its finds list because they are stored and fit its operators. Their order and paging are the search's (the latest message's date). A search typed in Later looks through All Mail, as any search does, and offers the server there too. The matches last as long as the words: a find the server matched only in text past its snippet lists again for later words once its body is downloaded (when it is opened, or the backfill reaches it). The list re-subscribes in place, keeping the pages it has read and its selection, as it does for the open conversation of an `is:unread` search ("Search"), so it grows rather than starting again from its first page, and reads on to the end of the finds when they take it past its pages, so the row still ends it. The row reads “Searching Gmail…” while the search runs (and until the rows it adds are read), then “Found 12 more on Gmail” (the conversations it added: found ones the list shows now and did not show before the search), “Nothing more on Gmail”, or “Couldn't search Gmail · Try again” (in a unified search the failed account by name, “2 accounts” or “your accounts”). New words, or another scope, cancel a search still running and bring the offer back with the new words' first page; an answer for an earlier search is dropped. VoiceOver hears the result once, when the list is read to its end.

## Calendar invitations

A message that carries a calendar invitation opens with a card (docs/DESIGN-LANGUAGE.md §5.14). SuperSparrow answers invitations and hands them to Calendar; it never keeps a calendar. The message's body, most often the sender's own rendering of the same invitation, starts folded under the card behind the quoted-text toggle's elision mark (“Show message”, and “.”): the shell decides it from the payload's card (`RenderPayload.Message.invitation`), never from the HTML, and still loads and measures the body's frame out of sight, so opening costs what it did and unfolding goes straight to the body's height. Only the frame folds: the body's banners (remote images, Original colors) stay in view under the mark, as they stay over folded quoted text. The fold lives on the card in the shell like shown quotes, so it lasts through the store's re-renders and is forgotten by a fresh render. The app sees every key before the page, and in the reader ↩ is Open and Space is Quick Look; the shell posts `focusMark` as keyboard focus lands on an elision mark or leaves one, kept per pooled slot, and while the reader's web view has focus and a mark has the page's, both keys go on to the page, which presses the mark.

- **Read at sync time, never at open.** When a body is fetched, the hydrator stores the invitation with it (`StoredBody.invitation`, `bodies.invitation_json`, docs/DATA-MODEL.md): Graph's, which the provider read from the event message's event, or the message's text/calendar part (Gmail, and the demo), read by `CalendarInvitationReader` for the user: the account's address only. No recipient of the message is taken for the user, because none is known to be theirs: a colleague beside them (Exchange mails one request to every guest), a mailing list the invitation went to alone, the colleague whose mailbox forwards here, or whoever the user forwarded it to would be shown as “You” and answered for. On Gmail's own domains an address matches without its dots or a plus tag (j.doe+work@googlemail.com is jdoe@gmail.com), as Gmail delivers them. A group attendee is never the user. With no match the card states no answer and offers none: an invitation that does not name the account (a forward, a Bcc, an assistant's copy of the boss's invitation, an invitation to the user's other account or another of their addresses) is not this account's to answer, since the answer would speak for someone it never invited. Two cases are answered unnamed, as the account (`CalendarInvitation.answersAsAccount`): Microsoft's, where the answer goes to the event in the user's own calendar, and an invitation to a group (CUTYPE=GROUP) the user may be on, which members answer as themselves (RFC 5546); Gmail then names the address the user's own Google Calendar copy lists as them (its `self` attendee, an alias included) when the answer finds that copy. “You” among the guests is the account the message came to, never another account. Only METHOD:REQUEST and METHOD:CANCEL (or an event marked cancelled) give an invitation; a reply, a published calendar and anything the reader cannot read whole give none, and the message shows no card rather than a wrong one. Messages without one are unchanged. Opening a message reads the stored facts; the card's words (`InvitationCardText`) are formatted when the payload is built, in this Mac's zone, which is cheap and follows the Mac when it travels.
- **The reader** is ours and small: unfolding (CRLF, LF or CR; a space or tab continues a line), parameters with quoted values, TEXT escapes, components nested at most four deep, at most 512 KB of text. DTSTART with DTEND, DURATION or neither (a date lasts the day, a time is an instant); DATE (all-day, held as the day's midnight read as UTC, never shifted), DATE-TIME in UTC, floating (held as its wall clock read as UTC) or with a TZID resolved through IANA names, vendor prefixes, the Windows names Outlook and Exchange send (`CalendarTimeZones`, after CLDR's table), the VTIMEZONE's X-LIC-LOCATION, or the VTIMEZONE's own yearly STANDARD and DAYLIGHT rules (a VTIMEZONE is found by its TZID with the TEXT escapes undone, so a name with a comma or a semicolon, which Outlook gives the zones it defines, matches the quoted TZID parameter); Outlook's all-day flag on midnight times, its end from DTEND or from a DURATION counted on the wall clock, so the event keeps its days. DTSTAMP is kept, to order two revisions with the same SEQUENCE. RRULE is described in words (`RecurrenceRule`: daily, weekly with days, monthly by day or nth weekday, yearly; COUNT and UNTIL); a rule with parts it cannot say reads “Repeats”, and one it cannot read at all gives no card. ORGANIZER and ATTENDEE with CN and PARTSTAT, each address exactly one plain address (its mailto percent escapes undone; a list, brackets, quotes, a comment, mailto headers, white space or a second `@` give none, so an organizer written to reach extra recipients leaves no one to answer and no answer); rooms and resources are left out. A repeating invitation's series wins over the occurrences listed after it.
- **Answering** is an operation (`MetadataChange.answerInvitation(InvitationAnswer)`), so it follows every rule of the outbox: the answer is written on the message in the enqueue's transaction (`MessageMetadata.invitationReply`, `messages.invitation_reply`, which no provider upsert writes), the card re-renders from the store, and the engine replays it. `InvitationAnswer` carries what a provider needs without reading the store (UID, SEQUENCE, RECURRENCE-ID, times, organizer, the attendee address the user answers as, Graph's event id) and the answer it replaced, which a give-up puts back. The same answer twice queues nothing; an answer changed before the earlier one went out replaces it in the outbox (see "User action" above), carrying over the answer the earlier one replaced. A give-up puts back only an answer that went out: when an answer is given up, a newer one queued while it was on its way (which named it as the answer it replaced) is rewritten in the give-up's transaction to name what the given-up one replaced. Only the latest revision of an invitation is answered: when a later message in the conversation (the messages its reader shows) carries the same UID and RECURRENCE-ID with a higher SEQUENCE, or the same SEQUENCE and a later DTSTAMP (`CalendarInvitation.supersedes`), the earlier card offers no answer and `answerInvitation` refuses it (`StoreError.conflict`), so an answer always carries the latest revision's UID, SEQUENCE, RECURRENCE-ID and times. Microsoft's cards all read the event as it is when the body is fetched, and Graph answers the event itself, so Graph states no SEQUENCE or DTSTAMP to compare. Gmail marks the user's Google Calendar copy (`events.list?iCalUID`, `events.patch` with `sendUpdates=none`), then mails the organizer an iMIP reply (RFC 6047: METHOD:REPLY, the user's ATTENDEE with PARTSTAT, the address that copy lists as the user when there is one, the same UID and SEQUENCE, `InvitationCalendarWriter`) through `messages.send`, at once and outside the composer's undo window, since the mail alone leaves that copy at “needs action” on the phone. Microsoft answers the event (`accept`, `tentativelyAccept`, `decline`, `sendResponse: true`). The outbox retries an answer whose request may have landed (a timeout, a dropped connection, a quit mid-request), and both the mail and the Graph call reach the organizer, so each step looks first: Gmail patches the copy only when it does not state the answer and mails only when no message with the answer's Message-ID (`InvitationAnswer.replyID`, made when the user answered) is in the mailbox; Graph posts only when the event does not state the answer. An answer to an event that is gone is given up at once and the previous one put back, so the card never shows an answer nothing sent.
- **Scopes, asked for at the first answer.** Answering needs Google's `https://www.googleapis.com/auth/calendar.events` or Microsoft's `Calendars.ReadWrite` (`AccountPermission.calendar`, `OAuthEndpoints`). Sign-in asks only for mail. The providers read the token's granted scopes (`AccessTokenProvider.grantedScopes`, the scope list the token endpoint returned; unknown grants nothing); without the scope the answer waits untried, the account reports `permissionsNeeded`, the card shows its permission notice and Settings › Accounts reads “Calendar permission needed” with Reconnect. Reconnect (`MailEngine.reconnect`) asks for the permissions queued work waits for plus those the stored token already grants (and Google is asked to `include_granted_scopes`), so signing in again never drops one. It saves the new tokens through the token manager (`AccessTokenProvider.replaceTokens`), which makes the keychain write on its own actor, with nothing between it and dropping the cached token: a healthy account's cached token would otherwise stand for up to an hour without the new scope, and a refresh begun with the old refresh token, whose save runs on the same actor, lands wholly before the write (which then replaces it) or after (still answering its callers, but neither saved nor cached), never between the write and the manager's knowing, where it would put the old grant back. The reconnect wakes the account, so the next drain sends the answer and the ask goes away.
- **Open in Calendar** writes the stored calendar text (the invitation as it arrived, or for Microsoft one written from its facts at sync time: a repeating event in its own zone's wall-clock time with a VTIMEZONE written from the Mac's zone data, one observance per kind of offset change over the span the repeat can run, since a rule expands in its start's zone and Graph states a repeat's days and end date in the event's zone; the end date becomes the end of that day there, in UTC; a repeating timed event whose zone the Mac does not know, or that names none, is written as its first occurrence alone, in UTC and with no RRULE, since Graph gives its times in UTC and its repeat in that zone and the two cannot be put in one frame without it, while the card still says how it repeats) to a folder of this run's own under the temporary directory, off the main thread, and opens it with Calendar (`com.apple.iCal`), which shows the event and offers to add it. No EventKit, so no calendar permission on the Mac.
- **Cost.** One more Graph request per event message's body; nothing more for Gmail unless the calendar sits behind an attachment id (an externalized text/calendar part, or an `.ics` file sent without one, of at most 512 KB): one `attachments.get`. An answer is one Gmail `messages.list` (5 units) and `messages.send` (100 units, outside the live estimate like every send) plus Calendar API calls on that API's own quota, or two Graph requests (the event's answer, then the POST). The permission check is local.

## Rendering

- Sanitize at sync time with SwiftSoup: strip `script`, `iframe`, `object`, `embed`, `form`, `input`, `meta`, `link`, `base`, event-handler attributes, `javascript:` URLs; keep `style` attributes and `<style>` blocks (the body is isolated in a sandboxed iframe); rewrite `cid:` images to `ss-cid://` URLs; replace remote image `src` with `data-ss-src` and remote `background=` with `data-ss-background`, and count them; strip `url(http…)` from inline CSS (counted, but not restorable by Load images); wrap detected quoted content in `<div class="ss-quote">`.
- The conversation view is one `WKWebView` showing a shell document (CSS and JS loaded once). Rendering a conversation is one `evaluateJavaScript("ss.render(json)")` that builds cards and places each body in `<iframe sandbox srcdoc>`. Inline images load through a `WKURLSchemeHandler` for `ss-cid` that reads attachment bytes from the local cache (fetching through `MailClient.attachmentData` when missing).
- An attachment chip's download (spec §5.17) shows once the fetch outlasts 150 ms, so a cached file never flashes it. `MailClient.attachmentData` takes the listed size and a progress handler: a provider that streams reports fractions as the bytes arrive, the attachment cache hands them to every caller of that download at most about ten times a second (`AttachmentProgressRelay`: the first and the last at once, one held fraction delivered when the interval is up), and the reader hops them to the main thread, never through the store, where `AttachmentDownloadBoard` turns them into the chip's contrail: determinate at the latest fraction, sweeping only while the size is unknown (no listed size and no Content-Length).
- Keep a pool of three warm web views. When the selection lands on a row, render the next row, the previous row, and the next unread conversation into spare views. Selection highlight moves immediately; rendering is debounced by 30 ms while a key repeats, and pre-rendering waits until the selection has rested for 150 ms.
- A read or star change in the shown conversation patches the card headers (`ss.flags`) instead of re-sending bodies. Whether a body has quoted text and how many remote images it parks are stored with it at sync time, so no render scans HTML.
- Dark mode: the shell adapts; email bodies get `color-scheme: light dark` and a per-message "show original" escape hatch.

## Performance budgets

Measured with `os_signpost` on a synthetic 100,000-message mailbox (see `Tests/SSCoreTests/Fixtures/SyntheticMailbox.swift`):

| Interaction | Budget |
|---|---|
| Move selection (`j`/`k`) | 16 ms |
| Open conversation, pre-rendered | 50 ms |
| Open conversation, body cached | 100 ms |
| Archive, star, mark read, snooze, unsubscribe (local: an unsubscribe's archive or snooze end and its queued request in one transaction) | 16 ms |
| Search keystroke, full text | 50 ms |
| Search the server: ↩ in the field or a click to the row reading “Searching Gmail…” | 16 ms (a state change on the main thread; the local results never wait for the network) |
| Launch to usable inbox | 500 ms |
| List refresh after a sync transaction | 50 ms |
| New mail visible with polling | 5 s while the app is active, 30 s in the background |
| Sanitize a 200 KB newsletter (sync time, off the main thread) | ≤ 2.5 × the SwiftSoup parse of the same HTML, about 21 ms on M-series (`SanitizerThroughputTests`) |

The sanitizer's budget is relative because the parse is a floor the module cannot go under (about 8.5 ms for that fixture on an M-series Mac); what sanitizing adds (the scrub, the CSS filter and its design facts, quote detection, text extraction, one serialisation) must stay within 1.5 parses on top. It runs at sync time and in the design-facts backfill, never when a message opens.

Rules that keep the budgets: search observations fetch their first page off the main thread and deliver only when the rows change; fixed row heights; no Auto Layout inside list rows; attributed strings built once per row and cached by conversation id plus a version; avatars decoded off the main thread, initials painted first; `DatabasePool` reads never wait on sync writes; sync writes batched: a changes page's upserts in one transaction and its deletes in another (up to 100 messages), its live marks committed first in their own (docs/DATA-MODEL.md, "Backfill marks"), and one transaction per listing page (100) or metadata chunk (10); no network on the launch path. Each live poll is a `sync.poll` signpost interval (subsystem `io.supersparrow.mac`, category `sync`), so new-mail latency can be read in Instruments. A search is two intervals. `list.search` (subsystem `io.supersparrow.mac`, category `list`) runs from the moment the list takes a search query (the field's text, sent 120 ms after the last keystroke, or another account picked while searching) to the moment the list has applied that query's first page, so it is read against the search keystroke budget; a query replaced before its rows arrive (more typing, a cleared field, another view) ends its interval with the marker `superseded`, so at most one is open; a query whose store read fails ends it then with `failed` (the store reports a stopped observation to its subscriber), so a broken search never reads as a slow or superseded one; and a blank query opens none. `store.search` (category `store`) spans each search read in the store, words or operators (`ConversationTable.fetch`: off the main thread for an observed first page or refresh, on the caller's thread for a further page), so Instruments shows how much of the wait is SQLite. A search of the server is a `sync.serverSearch` interval (category `sync`) in the engine. None carries the query text, a subject or an address.

An idle app keeps no timer faster than the poll. The storage sweeper and the size Settings shows keep none at all ("Storage bounds"), and nor does the snooze runner with nothing snoozed; with something snoozed it keeps one wait, to the soonest time, and while a due snooze waits for its account's check, one more of a minute at most ("Later"). The send queue and the sync line's sending count wait as "Send" describes. The sync line's "retrying in 30 s" is chosen again every second only while the line shows that count (Slow) in a window that is not occluded; behind Offline, Couldn't sync or Sign in required a retry ahead shows no count, and an outage keeps one ahead almost all the time, so those lines keep no timer, and a count in the tooltip alone is brought up to date as the pointer enters the line. Settings › Accounts ticks its clock only while its window is open and a row counts a retry down. The reader's shell looks every 300 ms for focus moving from one body to another only while a body has focus and the page has it; the web view tells the shell when the page may have it again (becoming first responder, its window becoming key), since focus returning to a body raises no event the shell hears.

## Security and privacy

- Tokens live in the Keychain. The database lives in `~/Library/Application Support/SuperSparrow/mail.sqlite` (0600).
- Remote images are blocked by default; loading them is per message, and loaded ones are cached on disk. The "Load remote images" preference is read for every body synced and by the reader, which renders each body that has not had its images loaded under a Content-Security-Policy (`img-src ss-cid: data:`, no other fetches), so turning the preference off takes effect at once, even for bodies stored while it was on.
- Open in Calendar writes an invitation's calendar text to a per-run temporary folder and hands it to Calendar; SuperSparrow reads and writes no calendar on the Mac (no EventKit). Answering an invitation needs the provider's calendar scope, asked for only when the user first answers.
- Attachments are written to a per-session temporary folder and quarantined as they are written (`com.apple.quarantine`, type email attachment, agent SuperSparrow), so Gatekeeper asks before anything in them runs; copies saved to Downloads or with Save As keep the mark. Opening a program or script (`.app`, `.command`, `.terminal`, `.jar`, `.pkg`, shell and AppleScripts, `.fileloc`) from the reader asks first, with Cancel as the default. Errors about these files are logged by domain and code only, since a file error names the attachment.
- No analytics, no crash reporting, no third-party services. Email content goes only to Google, Microsoft, and this machine.
- Unsubscribe and remote images the user chose to load are the only requests that reach a sender's servers. A one-click request is a POST to the sender's own server from this Mac (it carries the URI the sender chose, which can identify the user, and nothing else: no cookies, no credentials), and a page opens in the user's browser. A mailto request is mail sent from the user's account through Google or Microsoft. The URI is never logged above debug ("Unsubscribe").
