# SuperSparrow architecture

SuperSparrow is a local-first Mac mail client. Every interaction is a read or write against a local SQLite store; the network never sits between a keystroke and a pixel. This document is the contract every module is built against.

## Product scope for v1

Sparrow's shape, Superhuman's speed:

- Unified inbox across Gmail and Microsoft accounts, with a thin rail: the views as folder tiles at the top, the accounts at its foot to narrow to one account.
- Views: Inbox, Starred, Sent, Drafts, Trash, All mail. No folders, no labels, ever shown.
- The inbox always shows all of its mail. Gmail's Primary category and Outlook's Focused Inbox are stored (`inbox_section`) only to round-trip provider state; nothing filters or marks rows by them.
- Read conversations as stacked cards; quoted text folded; inline images; attachments with Quick Look.
- Actions: archive, mark read/unread, star, trash, restore. Undo for every action.
- Reply, reply all, forward, new message. Plain composer: bold, italic, underline, links, lists, quotes, attachments. Undo send (five seconds).
- Full-text search over subject, participants, and body, as you type.
- Keyboard first: `j`/`k` move, `e` archive, `s` star, `u` unread, `#` trash, `r` reply, `a` reply all, `f` forward, `c` compose, `/` search, `⌘1`..`⌘9` switch account, `⌘0` unified.
- Unread badge on the Dock icon. New-mail notifications.

Out of scope for v1: rules, snooze, send later, calendar invites, S/MIME, server drafts, on-premises Exchange, IMAP, multiple windows beyond compose. What comes after v1, and in what order, is `docs/ROADMAP.md`.

## Modules

```
SuperSparrowApp (AppKit, WebKit)  ──reads──▶  MailStoring (SQLite)  ◀──writes──  SyncEngine (actors)

```

- **SSCore/Model**: value types shared by everything. Already written; change only by agreement.
- **SSCore/Ports**: `MailProvider`, `MailStoring`, `MailClient`, `TokenStore`, `AccessTokenProvider`, sanitizer output. Already written.
- **SSCore/Store**: `SQLiteMailStore: MailStoring` using GRDB `DatabasePool` (WAL). Schema in `docs/DATA-MODEL.md`.
- **SSCore/Sync**: `AccountSyncer` (two lanes per account: the `LiveLane` actor owns the change cursor, replays the outbox and polls; the `BackfillLane` actor downloads older mail and missing bodies behind it), `QuotaBudget` (one per account, paces the backfill by `ProviderQuota`, see "Quota budget"), `OperationRunner` (outbox replay), `SendRunner` (undo window then send), `Hydrator` (bodies: a live path for new mail, a paced path for the backfill, on-demand fetches), `AttachmentCache` (attachment files on disk; a miss downloads through the provider into a partial file in one folder, swept before a run's first download since an interrupted run leaves its files there, charged as live spend, and concurrent callers share the download and its progress through an `AttachmentProgressRelay`), `MailEngine: MailClient` (facade wiring these together).
- **SSCore/Transport**: what both providers' transports share for downloads: `HTTPDownload` (one request whose 2xx body is written to a file as it arrives, through a data task with a task delegate, so a test session's stub `URLProtocol` drives it; an error reply's body comes back in memory for the transport's own status mapping) and `DownloadProgressMeter` (bytes into fractions that only rise and stop at 0.99 until the caller says the file is complete; measured against Content-Length unless the body is compressed, otherwise against the caller's estimate, and silent with neither).
- **SSCore/Auth**: `OAuthFlow` (PKCE, loopback redirect on 127.0.0.1, system browser), `KeychainTokenStore: TokenStore`, `TokenManager: AccessTokenProvider`, `ClientConfigurationStore` (reads `oauth-clients.json`).
- **SSCore/Render**: `HTMLSanitizer` producing `SanitizedBody` with SwiftSoup, plus `QuoteDetector` and `TextExtractor`.
- **SSGmail**: Gmail REST API client. Bootstrap = `users.messages.list` newest first with `-in:spam -in:trash -in:chats` (chats are hidden from All mail in Gmail too), hydrated via batch `messages.get?format=metadata` in batches of 10 parts: a part costs 20 units, so a batch is 200 units rather than 1,000 of the 6,000 a user may spend a minute. Throttled parts (429, or 403 `rateLimitExceeded`/`userRateLimitExceeded`) are sent again on their own after the largest part's Retry-After (or the refill time Google names), otherwise after 1, 2 and 4 s, keeping the parts already answered; such a wait is sat out inline up to 60 s once the call has fetched messages, and with nothing fetched yet a wait over 10 s is reported at once. A Retry-After over 60 s, or parts still throttled after the schedule, raise `ProviderError.throttled`, which discards that call's fetched messages. 404 parts are skipped, other failed or unanswered parts are fetched one by one, and a 401 part refreshes the token and resends the batch. The backfill listing (`backfillListing(page:limit:)`) is one `users.messages.list` call with the same `q` and `maxResults` as bootstrap, ids only (5 units a page); a bootstrap page token continues it. Gmail's per-user quota refusals carry no Retry-After header, so the refill time is read from "Retry after <RFC 3339>" in Google's error message; a time already past counts as unknown (nil). Each throttled response, or group of batch parts, is logged once at notice in the "gmail" category: HTTP status, Google's reasons and status, the request kind and the retry time public, the message text private. Changes = `users.history.list` from the `historyId` captured by `users.getProfile` before the head page; the live lane stores it as the cursor right after that page, not when the enumeration ends. Bodies via `messages.get?format=full`, MIME tree walked for text/html, text/plain, attachments and inline parts. Attachments the user opens (`downloadAttachment`) stream: the `messages.attachments.get` reply, a JSON object whose `data` is the file in base64url, is written to a file beside the cache's partial file as it arrives (`GmailHTTPClient.download`: the same token retry, status mapping and throttle log as every other request), then `GmailAttachmentDecoder` maps that file, finds the top-level `data` string and decodes it a slice at a time into the attachment cache, so neither the reply nor the file sits in memory whole. Its progress counts the reply's bytes against its Content-Length or, since Google usually sends it chunked, against the base64 length of the listed size plus the JSON around it, and stops at 99% until the file is decoded and written; with neither length it reports nothing. The oversized text parts a body fetch resolves still come in one response (`attachment(messageID:attachmentID:)`). Send builds RFC 5322 MIME (multipart/alternative inside multipart/mixed) base64url-encoded into `messages.send`, with `threadId` when replying; messages over 1 MiB of MIME go through the media upload endpoint (`uploadType=multipart`) instead because Gmail caps JSON request bodies. Changes map to `messages.batchModify` label edits.
- **SSGraph**: Microsoft Graph client. Bootstrap = `/me/messages?$orderby=receivedDateTime desc&$select=...` paging, excluding Deleted Items and Junk by parentFolderId. Changes = per-folder `/me/mailFolders/{id}/messages/delta` for inbox, sentitems, drafts, archive, deleteditems, junkemail and every other folder at any depth, found by walking the tree from `/me/mailFolders` (hidden folders left out) through `/childFolders` wherever a folder reports `childFolderCount` > 0, a level at a time down to 16 levels (`GraphProvider.maxFolderDepth`: far deeper than people file mail, it only stops a broken listing that keeps handing back new children from walking for ever, and a folder below it is left to the bootstrap listing and a reconcile), each folder kept once and its children listed once, so a duplicate or a cycle in the listing ends the walk, and a folder that answers 404 when its children are asked for (deleted since its parent was listed) is skipped with them, as the next walk would find. The walk costs the top-level listing plus one listing per folder with children, a request per page of 200 folders, sent one after another, so it is spread over calls and kept in the cursor (`GraphCursor.walk`: the folders found and the listings still to send, with the nextLink of one a step stopped partway through): the call that starts one looks up the system folders and sends the top level's first page, and each call after sends at most 5 listing pages (`GraphProvider.maxWalkPagesPerCall`, about a second; counted in pages, not listings, so a folder holding thousands of others is listed over several calls), so a tree with 60 folders that have children takes twelve polls and no poll, new inbox mail and all, waits for a whole tree. A listing that fails other than with a 404 holds up neither the step nor the poll: a throttle, a refused token, a cancellation or a reset fails the call as its next request would, and anything else (a 500, access denied, a 503 or 504 without Retry-After, a page that does not decode) ends the step with the listing left first in the walk for the next call to try again; after 3 calls (`GraphProvider.maxWalkAttempts`) the walk gives up on that listing and goes on with the rest (`GraphFolderWalk.gaveUp`). A walk starts at bootstrap, which takes its first two steps before the head page (the second only if the first sent no failed listing) and leaves the rest to the polls, and with the daily folder refresh (`GraphCursor.folderRefreshInterval`, counted from the walk's start by the cursor's `foldersResolvedAt`), never on an ordinary poll; the call that starts one keeps the system folder ids it had when a lookup fails. A cursor without the `folderScope` marker was listed two levels deep by an earlier version, so its walk is due on its first poll rather than a day after that listing. A folder the walk finds, at any depth, gets its delta and starts seeding at once (a folder made in Outlook is found by the next walk). One it did not find stays on its delta link, listed in the cursor's `missed`, and is dropped when the next walk misses it too: a walk spread over polls can miss a folder moved meanwhile out of a listing still to come into one already sent, and a deleted folder usually goes sooner, when its delta answers 404. A walk that gave up on a listing drops nothing and adds nothing to `missed`, since it did not look under every folder. A folder found late misses nothing, since its first round lists its whole content. Each delta is seeded without a `$filter` (the only filter message delta accepts, `receivedDateTime ge`, also limits which messages the delta tracks, so reads, moves and deletes of older mail would never be reported); inbox, sentitems and drafts, plus any folder partway through a round on a nextLink, are drained round-robin on every poll until each reaches its deltaLink or about `limit` items are collected; every other folder already on its deltaLink (a quiet folder) waits for a full visit, which starts at most once every 30 s (`GraphCursor.fullVisitInterval`; the cursor keeps when the latest started as `fullVisitAt`, and a cursor without it starts one on its next call) and is spread over calls: each call polls the next quiet folders in id order after the last one the visit polled (`fullVisitAfter`, so a folder added or dropped meanwhile shifts nothing), 2 for every second since the last call (`polledAt`) and never more than 20 (`GraphCursor.quietVisitsPerSecond`, `maxQuietVisitsPerCall`). So a quiet poll is never a heavy page for the live lane (the priority folders, 20 quiet ones, a seed page and a walk step stay under the 34 requests that make one, "Live lane" above) and the quiet folders' cost never holds back the inbox's next poll, however large the tree. At the live lane's 5 s interval a mailbox with 40 folders spends about 1,100 of Outlook's 10,000 requests per 10 minutes per mailbox instead of 4,800, each quiet folder still polled every 30 s, and one with 200 folders about 1,600, each quiet folder polled about every 100 s; a visit of all 200 in one call cost 200 requests, and the live lane held each next poll, the inbox's with it, back about 36 s to pay for that. Polled every 30 s in the background, a visit of more than 20 quiet folders takes more than one poll. Every other folder still in its first round gets one seed page per poll (`maxSeedPagesPerCall` = 1), one folder at a time in folder order, and a seeding folder's nextLink alone does not set `hasMore`, so new inbox mail is never held behind a re-listing of the mailbox. The first round lists each folder once (a non-priority folder's over several polls, a page per poll), which also repairs anything the offset-paged bootstrap skipped. A removal a delta reports is looked up by id in `$batch` before it counts as a deletion, since a move out of a folder reads the same. Each page reports the requests its call sent (`requestCount`, tallied by the transport: every attempt, a `$batch` as its parts), which the live lane is charged. The opaque cursor is a resumable record of each folder's place: a JSON map of folder id to deltaLink, plus each folder's in-progress nextLink, the well-known folder ids, when the folder list was last resolved, a folder walk under way, the folders the last walk missed, when the latest full visit started and how far it has got, and when the last call ran. The backfill listing is the protocol's default over bootstrap, since a Graph page carries its metadata inline. Bodies via `/me/messages/{id}?$select=body,uniqueBody` with `Prefer: outlook.body-content-type="html"` and `/attachments` (Content-IDs selected as `microsoft.graph.fileAttachment/contentId`, since the base attachment type has none). An attachment's raw bytes stream from `/me/messages/{id}/attachments/{id}/$value` into the attachment cache as they arrive (`GraphHTTPClient.download`: the same token retry, request tally and status mapping as every other request), counted against Content-Length or, without one, the listed size (Graph's listed size can run over the file's, so a stated length wins); an attachment with no `$value` (an item or reference attachment: a 404 or another server error) falls back to its base64 `contentBytes` in JSON, in one response. Send via `/me/sendMail` while attachments fit its 4 MB request, otherwise via a draft (`POST /me/messages`); replies via `/me/messages/{id}/createReply` then PATCH then `/send` so Outlook threads them. Draft attachments of 3 MB and more go through `createUploadSession` in 3.125 MiB chunks; a draft whose filling fails is deleted so retries leave no orphans. Changes map to PATCH `isRead`/`flag` and POST `/move`. Batch with `$batch` (20 per call). 429, and 503 with Retry-After, map to `throttled` with the Retry-After value, and each throttled response is logged once at notice in the "graph" category (status, Graph error code, Retry-After, nothing about the mail); a 503 or 504 without Retry-After is still a network error.
- **SSCore support folders** (`ListSupport/`, `ConversationSupport/`, `ComposeSupport/`, `ShellSupport/`): the pure, testable halves of the app's surfaces (row text and layout, the reader's render payload and shell, reply recipients and drafts, the sync line, undo order, toasts' words). `Model/AccountLabels` is the one place an account's monogram, tile letter, name and From title are derived, so every surface shows the same ones.
- **SSDesign**: the Quire design runtime and every component, as a library the app links. See "Design" below.
- **SuperSparrowApp**: `AppDelegate`, `MainWindowController` (NSSplitViewController: account rail, message list, conversation), `MessageListViewController` (NSTableView, fixed rows, manual layout, cached attributed strings), `ConversationViewController` (warm `WKWebView` pool, `ss-cid` scheme handler, quick reply), `ComposeWindowController`, `KeyboardRouter`, `SettingsWindowController` (SwiftUI), `NewMailNotifier`, the Dock badge, and, in debug builds, the Design Gallery (`Design/`, below).

## Data flow

1. **Add account**: `MailClient.addAccount` → `OAuthFlow` opens the system browser → loopback receives the code → tokens go to Keychain → provider `profile()` → `Account` row → engine starts the account's two lanes.
2. **Head page and cursor first**: an account without a change cursor gets one from its newest page. The live lane fetches `bootstrap(page: nil)` (100 messages, with the cursor the provider captured before listing), saves a `BootstrapState` holding that cursor and no page, upserts the head in one transaction, saves the state again with its next page, then the cursor, and fetches the newest bodies. A crash or a failed write anywhere after the first save leaves a state whose cursor the next launch adopts, so polling covers every head row (even one newer mail has pushed off a later head) and the backfill lists from the top; so does a download the single-loop engine left in progress, except that its backfill resumes at the saved page. The first poll brings in everything since. However large the mailbox, new mail flows from the first poll on (no gap: the cursor predates the listing, and duplicates are idempotent).
3. **Live lane**: replays the outbox, then polls `changes(since:)` until `hasMore == false`, saving the cursor after each page: every 5 s while the app is frontmost and every 30 s otherwise (the schedule runs on the monotonic clock, so setting the Mac's clock back cannot postpone a poll), plus on `syncNow`, activation, waking from sleep and the network coming back. Only Sync Now and Reconnect (`syncNow`, `WakeReason.poll`) try a parked account's token again; the automatic checks (`checkForMail`, `WakeReason.check`) leave it parked, so a refused keychain's prompt never comes back with nobody asking, and the token provider, shared by every account, is never held on that prompt. It then fetches the bodies of the newest 20 messages new to the store or back from Spam (not other stored ones whose labels or folder changed, and not spam), 2 at a time and only as many as its share of the quota pays for, and leaves the rest to the backfill; after a head page (a new account, or a reset) it fetches the newest 20 whatever the share holds. It never waits on the backfill, so a throttled download cannot hold back new mail, archive or star; what it can put off it fits to its own share of the quota ("Quota budget"): after a changes page that said `hasMore` or was heavy (more than a tenth of the share: about ten Gmail messages, or 34 Graph requests), the next page, of the same poll or the next, waits outside the cycle until the share covers another page like it, so a catch-up larger than the share goes on at about a page a minute on Gmail, and so do the polls of a busy mailbox that each bring a heavy page, while the outbox keeps moving. After a light page the next poll's first page goes whatever the share owes (the bodies of an opened conversation count against it), so the steady poll (2 Gmail units) and a few new messages never wait, and nor does Sync Now unless a run or a heavy page came just before it. While a backfill runs, it marks each page's upserts and deletes (`markLiveChanges`) before writing them. A rejected cursor (`resetRequired`) no longer wipes anything: the live lane takes a fresh head page and cursor and only then replaces the old backfill (its state first, with nowhere to resume from, then its marks) with a reconciling one. A reset whose head fails leaves the running backfill as it was, and one whose writes fail leaves a reconcile that lists from the top before it sweeps, never one resumed with half its marks. Its throttles and failures back off up to 60 s (a provider's Retry-After is honoured up to that cap: a time hours away is more often a skewed clock than advice), and a refused token or keychain parks both lanes until Sign in or Sync Now.
4. **Backfill lane**: downloads the rest behind the live lane, paced by the account's quota budget. One listing page at a time from the saved page token (Gmail: ids only, then metadata ten at a time for the ids the store lacks, each chunk written as it arrives; Graph: metadata inline), written with `writeBackfillMessages`, which skips whatever the live lane wrote or deleted meanwhile, so a page fetched before a live change can neither undo it nor bring back a deleted message (docs/DATA-MODEL.md, "Backfill marks"). The state is saved after every page, so a quit resumes there, and a stored page token the provider rejects restarts the listing from the top. Each page is followed by one paced body batch (inbox first, newest first); once the listing completes, the lane fetches the remaining bodies, then sleeps until woken or for 5 minutes. Every body batch is followed by one local batch of design facts for bodies stored before v3. At launch the lane waits for the live lane's first cycle, so a token or keychain prompt is asked for once, and it looks at the park before every request, so a turn under way stops once the account is parked. A reconciling backfill also refreshes stored rows and records every id it lists; when complete it removes the stored messages the provider no longer listed, except those a live operation targets, and those only if the provider, asked just before (`metadata(for:)`), no longer has them: their deletion sat in the expired history, so no poll would report it. A throttle pauses this lane alone (`AccountSyncStatus.backfillPausedUntil`), and its errors never change the live phase. A failure backoff ignores wakes, except a replaced backfill and bodies of new mail the live lane hands over after a poll that went through (the network is back).
5. **User action**: UI calls `MailClient.perform` → `store.enqueue(operation)` applies the change to the targets and inserts the operation in one transaction → observations fire → `OperationRunner` replays pending operations in order per account with exponential backoff; `confirmed` operations are deleted; `uncertain` ones (timeouts) are left for the next poll to settle.
6. **Pending operations win**: when a poll upserts provider state for a message that has a pending or in-flight operation, the store re-applies the pending changes on top of the provider state so an archived thread cannot pop back into the inbox before the provider catches up.
7. **Send**: `MailClient.send` stores a `PendingSend` with `sendAfter = now + undoWindow`; `SendRunner` sends it after the window; the sent message appears via the next poll (Gmail returns `threadId`, Graph threads by `conversationId`).

## Quota budget

Each account has one `QuotaBudget`, a token bucket in the provider's own units (`ProviderQuota`). Gmail allows 6,000 units per user per minute: `messages.list` costs 5, `messages.get` 20 with metadata and 60 in full, `messages.attachments.get` 5, `history.list` 2. Outlook allows 10,000 requests per 10 minutes per mailbox, so 1,000 a minute, and Graph counts each request inside a `$batch` on its own: metadata fetched by id costs 1 request per message, a listing page with metadata inline 1, a body 2 (the message and its attachments), an attachment's bytes 1 (its `$value`). The backfill lane may spend two-thirds of the allowance, takes its units before every request and keeps at most 2 in flight; the live lane never waits for the backfill's units and records an estimate of its spend in the same bucket: each head page (plus, on Gmail, 20 units of metadata per message; Graph's carries it inline), each changes page, each body it fetches, each message the user opens and each attachment the attachment cache downloads (5 Gmail units, 1 Graph request, recorded before the request goes out; a file already cached costs nothing), since a file the user opens, saves or sees inline is as much the user's action as an opened message and never waits. A Gmail changes page is the call plus 20 units per message; a Graph one is every request the call reports it sent (`ChangesPage.requestCount`): a delta GET per folder it visits, a folder walk step's lookups and listings, and a `$batch` part per removal it looks up, three on a quiet poll, about thirteen while a full visit goes on and over a hundred on a page of removals. A Graph head page is likewise every request its call reports (`BootstrapPage.requestCount`): the system folder lookups, the folder walk's first steps and the page. The backfill's listing from the top takes one page's units before it goes out and, when the call reports more (Graph's runs the same lookups and steps), the rest after (`QuotaBudget.recordBackfill`), so its next request waits for them. The estimate leaves out the outbox and sends. The third left over is headroom for that and for the live lane's own spend (a poll every 5 s, a head page of about 2,005 Gmail units, the newest bodies), so new mail never queues behind older mail and a busy live lane slows the backfill, never the reverse. A throttle on the backfill halves its rate and pauses it until the provider's retry time, or 15 s doubling to 10 minutes; every quiet minute wins back a tenth of the rate. The live lane's spend also comes out of a share of its own, the third the backfill leaves (2,000 Gmail units a minute), refilling at that rate, holding a minute of it and owing a minute, or all of a single cost beyond that (so a Graph page of a thousand requests is paced by what it cost, not by a minute's worth): nothing waits on it, but the live lane reads it before what it can put off, the next page after a run or heavy changes page and prefetching the bodies a poll brought, so its own burst stays within the provider's limit as well. A head page's newest 20 bodies do not wait for it: on Gmail the head alone (2,005 units) spends the whole share, and Gmail took about 5,000 units within 12 s without refusing, so the head and 20 bodies (3,205) stay inside what it accepts. Gmail refuses a few thousand units spent in a few seconds well before a minute's 6,000 (two pages of 137 and 56 changes, 20 bodies and an opened conversation's attachments did it), so a changes page is 100 messages, about 2,000 units, the whole share. The demo's made-up mailbox is unmetered.

## Rendering

- Sanitize at sync time with SwiftSoup: strip `script`, `iframe`, `object`, `embed`, `form`, `input`, `meta`, `link`, `base`, event-handler attributes, `javascript:` URLs; keep `style` attributes and `<style>` blocks (the body is isolated in a sandboxed iframe); rewrite `cid:` images to `ss-cid://` URLs; replace remote image `src` with `data-ss-src` and remote `background=` with `data-ss-background`, and count them; strip `url(http…)` from inline CSS (counted, but not restorable by Load images); wrap detected quoted content in `<div class="ss-quote">`.
- The conversation view is one `WKWebView` showing a shell document (CSS and JS loaded once). Rendering a conversation is one `evaluateJavaScript("ss.render(json)")` that builds cards and places each body in `<iframe sandbox srcdoc>`. Inline images load through a `WKURLSchemeHandler` for `ss-cid` that reads attachment bytes from the local cache (fetching through `MailClient.attachmentData` when missing).
- An attachment chip's download (spec §5.17) shows once the fetch outlasts 150 ms, so a cached file never flashes it. `MailClient.attachmentData` takes the listed size and a progress handler: a provider that streams reports fractions as the bytes arrive, the attachment cache hands them to every caller of that download at most about ten times a second (`AttachmentProgressRelay`: the first and the last at once, one held fraction delivered when the interval is up), and the reader hops them to the main thread, never through the store, where `AttachmentDownloadBoard` turns them into the chip's contrail: determinate at the latest fraction, sweeping only while the size is unknown (no listed size and no Content-Length).
- Keep a pool of three warm web views. When the selection lands on a row, render the next row, the previous row, and the next unread conversation into spare views. Selection highlight moves immediately; rendering is debounced by 30 ms while a key repeats, and pre-rendering waits until the selection has rested for 150 ms.
- A read or star change in the shown conversation patches the card headers (`ss.flags`) instead of re-sending bodies. Whether a body has quoted text and how many remote images it parks are stored with it at sync time, so no render scans HTML.
- Dark mode: the shell adapts; email bodies get `color-scheme: light dark` and a per-message "show original" escape hatch.

## Design

The design language is Quire (`docs/DESIGN-LANGUAGE.md`). `docs/design/tokens.json` is its single source; nothing downstream is edited by hand.

```
docs/design/source/tokens_def.py ──sh docs/design/source/make.sh (python3)──▶ docs/design/tokens.json
                                                                             docs/DESIGN-LANGUAGE.md, docs/design/specimen.html
docs/design/tokens.json ──swift scripts/tools/quire-tokens.swift──▶ Sources/SSDesign/Generated/QuireTokens*.swift
                                                                    Sources/SSCore/ConversationSupport/QuireCSS.swift
                                                                    Tests/SSDesignTests/Generated/*.swift
                                                                    Resources/Assets.xcassets (AccentColor)
docs/design/tokens.json ──swift scripts/tools/app-icon.swift──▶ Resources/AppIcon.icns (iconutil, macOS 15)
                                                                Resources/AppIcon.icon (Icon Composer document, macOS 26+)
```

- **SSDesign** (`Sources/SSDesign`): the design runtime as a library, so it can be unit-tested; the app depends on it. AppKit, SwiftUI and QuartzCore only: no SSCore, GRDB or WebKit. Generated tokens (`NSColor.q…` and `Color.q…` providers with the Graphite branch, account and avatar palettes, `QuireFont.Role`, `Quire.Space`/`Radius`/`Border`/`Elevation`/`Motion`, `Quire.Layout.<Group>.<name>`, icons, glyphs, the cheat sheet) sit in `Generated/`; beside them the hand-written runtime: `QuireFont` (cached fonts, exact line heights, the New York coverage test, and the Font setting: under SF Pro every New York role resolves to its sans twin before a font is looked up, so caches key on the role actually set), `QuireEnvironment` (Graphite, Increase Contrast, Reduce Motion, Reduce Transparency, and the Font setting the app pushes into it at launch and on every change, as a thread-safe snapshot plus a change notification; the typeface is part of `cacheKey(for:)`, and every view that holds a font or a laid-out string re-applies on the notification, so a switch is live everywhere, the reader's pooled web views included, without a relaunch or a re-measure), `QuireLayerColors` (re-resolves `CGColor`s on appearance and environment changes), `Quire.Motion` (token animations, Reduce Motion fallbacks, `finishAll()`), `QuireGlyph`/`QuireSVGPath` and `QuireSymbol`.
- **Reader CSS**: `QuireCSS.head` lives in SSCore because the reader shell is built there and SSCore does not import AppKit. It is byte-identical to the specimen's `<style>` head (`QuireCSSTests`).
- **Components**: `Sources/SSDesign/AppKit` holds the AppKit components: `QuireControl` and the controls built on it (`QuireButton`, `QuireIconButton`, `QuirePopUpButton`, `QuireCheckbox`, `QuireRadioGroupView`, `QuireToggle`, `QuireTextField` with its secure variant, `QuireSearchField`), `QuireBannerView`, the slips (`QuireSlipView` for toasts, `QuireUndoPanelView`, `QuireSequenceHUDView`), `QuireKeycap`, `QuireAvatarRenderer`, `QuireHairline`, and `QuireWindowChrome`, which configures and measures the main and composer windows' title bars. `Sources/SSDesign/SwiftUI` holds the Settings controls (`QuireButtonStyle`, `QuireFieldStyle`, `QuireSecureField`, `QuireRadioGroup`, `QuireBanner`, `QuireAccountRow` and the rest). The app composes them and defines no colours, fonts or metrics of its own.
- **Accent and icon**: `scripts/build-app.sh` compiles `Resources/Assets.xcassets` and `Resources/AppIcon.icon` into `Contents/Resources/Assets.car` with `xcrun actool` (Xcode), and sets `NSAccentColorName = AccentColor` and `CFBundleIconName = AppIcon`; the drawn `AppIcon.icns` is copied beside it as `CFBundleIconFile`. Without actool it warns: the bundle falls back to the system accent and the `.icns` alone (no dark or tinted icon on macOS 26 and later). A macOS app icon set cannot carry dark or tinted images, which is why the icon is an Icon Composer document.
- **Design Gallery** (`Sources/SuperSparrowApp/Design`, debug builds only): Debug › Design Gallery, or `--gallery`, opens every SSDesign component in every state on a page laid out like section D of `docs/design/specimen.html`, with a bar that forces the appearance, the font and the Quire environment (Graphite, Increase Contrast, Reduce Motion, Reduce Transparency) for that window. `--snapshot-gallery=<png>` renders the whole page. Its page furniture (`DesignGalleryStudio`) copies the specimen's, which is not a Quire token and appears on no other screen.
- **Tests**: `Tests/SSDesignTests` asserts every contrast pair in four modes (and every Graphite pair), the account-palette rules, the radius scale, row metrics across scripts, the glyph paths, and that the runtime still equals `tokens.json`. The colour math is a port of `docs/design/source/colorlib.py`; a pair that fails in Swift but passes in python is a port bug.

Regenerate after changing tokens:

```
sh docs/design/source/make.sh               # tokens.json, the spec and the specimen, from the python sources
swift scripts/tools/quire-tokens.swift      # Swift runtime, reader CSS, generated tests, accent asset
swift scripts/tools/quire-tokens.swift --check   # exits 1 and lists stale outputs; scripts/test.sh runs it first
swift scripts/tools/app-icon.swift          # the app icon, after a change to the mark, layout.appIcon or the inks
```

## Launch options

Debug aids, read by `LaunchOptions` (and `--snapshot-state` by the main window). They never touch the user's mail: the welcome and alert snapshots run over a throwaway store, and the others need `--demo`. Every path is absolute. Only `--demo` and `--reset-demo` exist in release builds; a release build ignores every other option here, so nothing can make it write its windows (Settings shows the configured OAuth client ID) to a path a caller chooses. The Design Gallery (`Sources/SuperSparrowApp/Design`) is compiled only into debug builds. Snapshots of the main window or a composer use the default frame, split and composer size, ignore the pointer, and never save a size.

| Option | What it does |
|---|---|
| `--demo` | Opens the two made-up demo mailboxes (`demo.sqlite`, §5.43) instead of the user's accounts. |
| `--reset-demo` | Wipes the demo store first; implies `--demo`. |
| `--appearance=light` / `=dark` | Forces the app's appearance, so one machine can check both. |
| `--font=newyork` / `=sf` | Forces Settings › General › Font for this process only (nothing is saved), so one machine can check both faces. |
| `--snapshot=<png>` | In demo mode, opens the first inbox conversation and writes the main window with the reader composited in. The app keeps running. |
| `--snapshot-compose=<png>` | In demo mode, writes a reply composer for the first inbox conversation. The app keeps running. |
| `--snapshot-state=<a,b,…>` | Debug. Puts the main window in named states before `--snapshot`: `key`, `notkey`, `several` (three conversations selected), `minimal`, `narrowed`, `search`, `toast`, `adding`, `signin`, `reconnect`, `focus-rail`, `focus-folder`, `focus-action`, `hover-demo`, `hover-masthead`, `many-accounts` (six made-up accounts in the rail only, to show the account stack scrolling), `ic`, `graphite`. |
| `--snapshot-welcome=<png>` | Writes the welcome screen over a throwaway store, then quits. |
| `--snapshot-welcome-states=<png>` | Every welcome state of §5.39, stacked, then quits. |
| `--snapshot-settings=<png>` | Every Settings tab, stacked, then quits (implies `--demo`). Settings › OAuth shows the configured client ID. |
| `--snapshot-settings-states=<png>` | The Settings states of §5.40 (adding, add failed, reconnecting, empty, the OAuth notices, Saved), stacked, then quits. |
| `--snapshot-cheatsheet=<png>` | The main window with the keyboard cheat sheet open, then quits. |
| `--snapshot-hud=<png>` | The main window with the g-sequence HUD showing, then quits. |
| `--snapshot-alerts=<png>` | The alert inventory (§5.33) as the system draws it, then quits. |
| `--gallery` | Debug. Opens the Design Gallery at launch. |

## Performance budgets

Measured with `os_signpost` on a synthetic 100,000-message mailbox (see `Tests/SSCoreTests/Fixtures/SyntheticMailbox.swift`):

| Interaction | Budget |
|---|---|
| Move selection (`j`/`k`) | 16 ms |
| Open conversation, pre-rendered | 50 ms |
| Open conversation, body cached | 100 ms |
| Archive, star, mark read (local) | 16 ms |
| Search keystroke, full text | 50 ms |
| Launch to usable inbox | 500 ms |
| List refresh after a sync transaction | 50 ms |
| New mail visible with polling | 5 s while the app is active, 30 s in the background |
| Sanitize a 200 KB newsletter (sync time, off the main thread) | ≤ 2.5 × the SwiftSoup parse of the same HTML, about 21 ms on M-series (`SanitizerThroughputTests`) |

The sanitizer's budget is relative because the parse is a floor the module cannot go under (about 8.5 ms for that fixture on an M-series Mac); what sanitizing adds (the scrub, the CSS filter and its design facts, quote detection, text extraction, one serialisation) must stay within 1.5 parses on top. It runs at sync time and in the design-facts backfill, never when a message opens.

Rules that keep the budgets: search observations fetch their first page off the main thread and deliver only when the rows change; fixed row heights; no Auto Layout inside list rows; attributed strings built once per row and cached by conversation id plus a version; avatars decoded off the main thread, initials painted first; `DatabasePool` reads never wait on sync writes; sync writes batched: a changes page's upserts in one transaction and its deletes in another (up to 100 messages), its live marks committed first in their own (docs/DATA-MODEL.md, "Backfill marks"), and one transaction per listing page (100) or metadata chunk (10); no network on the launch path. Each live poll is a `sync.poll` signpost interval (subsystem `io.supersparrow.mac`, category `sync`), so new-mail latency can be read in Instruments.

## Security and privacy

- Tokens live in the Keychain. The database lives in `~/Library/Application Support/SuperSparrow/mail.sqlite` (0600).
- Remote images are blocked by default; loading them is per message, and loaded ones are cached on disk. The "Load remote images" preference is read for every body synced and by the reader, which renders each body that has not had its images loaded under a Content-Security-Policy (`img-src ss-cid: data:`, no other fetches), so turning the preference off takes effect at once, even for bodies stored while it was on.
- Attachments are written to a per-session temporary folder and quarantined as they are written (`com.apple.quarantine`, type email attachment, agent SuperSparrow), so Gatekeeper asks before anything in them runs; copies saved to Downloads or with Save As keep the mark. Opening a program or script (`.app`, `.command`, `.terminal`, `.jar`, `.pkg`, shell and AppleScripts, `.fileloc`) from the reader asks first, with Cancel as the default. Errors about these files are logged by domain and code only, since a file error names the attachment.
- No analytics, no crash reporting, no third-party services. Email content goes only to Google, Microsoft, and this machine.

## Testing

`scripts/test.sh` checks that the generated design files match `tokens.json`, then runs every target:

- **SSCoreTests**, **SSGmailTests**, **SSGraphTests**: the store, engine, providers, sanitizer and the surfaces' pure halves.
- **SSDesignTests**: the generated contrast, palette, radius and metric tests (`Generated/`, never edited) and the hand-written component, font, glyph and window-chrome tests.
- **SuperSparrowAppTests**: the app's own windows. `MainWindowHarness` builds a main window over a throwaway store in a temporary directory, and the draft tests point the shared draft store at a temporary folder, so no test touches real mail, real drafts, the Keychain or the network.

Gated runs, skipped unless asked for:

- `SS_PERF=1 swift test -c release --filter …`: the list benchmark (`MessageListPerformanceTests`, `SS_LIST_PERF_MESSAGES` sets the mailbox size, 100,000 by default), the store, row-text, layout and sanitizer throughput measurements.
- `SS_UI_TESTS=1 swift test --filter …`: renders that write files or need a live web view (`ConversationRowStatesRenderTests`, the reader shell's web view test).
- `QUIRE_GALLERY_OUT=<dir>` (`ComponentGalleryTests`) and `QUIRE_GALLERY_DIR=<dir>` (`SettingsGalleryTests`): the component galleries in all four modes, as PNGs.

What each layer covers:

- Store: contract tests against in-memory GRDB covering upsert, conversation summaries, the unified query, pending-operations-win, FTS, and paging.
- Engine: fake provider with scripted pages (listings with metadata inline or ids only), throttling of either lane, the live lane's share of the quota (budgets on a clock the test moves), reconcile after a reset, an adopted single-loop download, and uncertain outcomes; assert store state after each step and after a simulated restart.
- Providers: JSON fixtures recorded from real APIs (anonymized) decoded through the real mappers; MIME builder round-trips; attachment downloads through a stub `URLProtocol` that sends a reply in timed chunks, so the streaming path, its progress and its error mapping run as on the network.
- Sanitizer: attack fixtures (script injection, event handlers, `javascript:` URLs, CSS exfiltration, cid spoofing) and real Gmail/Outlook HTML shapes.
- UI: the main window, list, multi-selection, menus, undo order, drafts, sign-in and the composer's chrome through `SuperSparrowAppTests`; the snapshots above for looking at.
