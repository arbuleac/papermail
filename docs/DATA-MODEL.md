# Data model (SQLite via GRDB)

One database per user: `~/Library/Application Support/SuperSparrow/mail.sqlite`, WAL mode, `DatabasePool`. Every table that holds account data carries `account_id` and cascades on account delete. All timestamps are Unix epoch milliseconds (INTEGER).

### The file
`auto_vacuum` is written into the file with its first page and fixed from then on: only a full VACUUM changes it. The store creates a new file with `auto_vacuum = INCREMENTAL` (`MailSchema.prepareAutoVacuum`, run by GRDB's `prepareDatabase` on the writer while the file is still empty, before WAL mode writes the first page), so the engine can hand the pages an eviction or a delete frees back to the file system a bounded step at a time (`PRAGMA incremental_vacuum(N)`, docs/ARCHITECTURE.md "Storage bounds"). A file created by an earlier build keeps `NONE`: switching it needs a full VACUUM (twice the disk, the writer held throughout), which the store never runs, so the engine's vacuum steps do nothing there (`reclaimFreePages` answers nil). Such a file stops growing while SQLite reuses its free pages, but does not shrink. The size Settings shows leaves those free pages out (`MailboxFootprint`), so it follows a clean-up even in such a file. A later release could compact it with `VACUUM INTO` a new file at a quiet launch and swap the files.

### message_fts (FTS5, external content = bodies/messages)
Columns (v12): `subject`; `sender`, the From name and address; `recipients`, every To, Cc and Bcc name and address; `body`, `bodies.plain_text` (kept when a body is evicted), or `messages.snippet` while the message has no body row (v13), so metadata alone (the first download's, a search of the server's) is searchable by the words the provider showed for it. Before v12 one `participants` column held the From, To and Cc names and addresses (no Bcc). The content table is the view `message_fts_content` over `messages` LEFT JOIN `bodies`, which builds `sender` and `recipients` from the address JSON (recursive CTEs, since FTS5 reads the view with virtual tables disallowed). Tokenizer `unicode61 remove_diacritics 2`. `rowid` = `messages.rowid`. Maintained by the store on upsert (only when the subject, From, To, Cc, Bcc or snippet changed: `MessageTable.IndexedFields`, which must name every column the view reads, since FTS5 removes an entry only with the values it was indexed with), on every body save (whole or already evicted) and on delete, each bracketed by a delete of the old entry and an insert of the new from the same view (no triggers, so inserts stay in the same transaction and remain explainable). An eviction leaves the entry alone.

A search (docs/ARCHITECTURE.md "Search") matches one MATCH expression per message: words across every column, `from:` in `sender`, `to:` in `recipients`, `subject:` in `subject`, the negated ones after NOT. It reaches its conversations by one of two plans (`ConversationTable.SearchPlan`), chosen per query from how many messages match, so the cost follows either the hits or the page, never the mailbox. *Hits first*, for fewer than 5,000 hits: each hit is looked up by its rowid and its conversation key kept, and those conversations are joined (the hits the outer loop, CROSS JOIN) and sorted. *Newest first*, for more, and for a match whose terms are all negated: the conversations are walked on `conversations_latest` in date order, each asked through the covering index `messages_by_conversation` whether one of its messages is in the set the match produced (`+m.rowid IN (SELECT rowid FROM message_fts WHERE …)`, or NOT IN), until the page is full. The other operators are predicates on the summary row (`unread_count`, `is_starred`, `has_attachments`, `latest_date_ms`, the view flags), which the walk reads from the index; results order by `latest_date_ms`, an `in:inbox` search's too (its rows show their latest message's date, not a return's). The conversations a search of the server found (`ConversationQuery.serverMatches`, docs/ARCHITECTURE.md "Server search") join the hits by key (a UNION with the hits, or a second test beside the walk's), so they join whatever their stored text holds and the predicates, the order and the paging apply to them alike.

### pending_sends

### Body design facts
Worked out once by `HTMLSanitizer` at sync time and stored with the body, so the reader never scans HTML to decide how to set a message (docs/DESIGN-LANGUAGE.md §8.4, §8.5). The render payload carries them per message (`typesetting` as its name, `declaresColors`, `coveredByNewYork`, next to `hasBody`) together with the conversation account's `inkSlot`.
- **typesetting**: `plain` when the body came from the text/plain part (no HTML part, a blank one, or one that failed to parse). `unstyled` for HTML with no author styling: no `style` attribute, body style or `<style>` element (after filtering) declaring anything beyond the neutral text-flow and spacing properties (`margin*`, `padding*`, `border*`, `direction`, `unicode-bidi`, `text-align`, `word-wrap`, `overflow-wrap`, `word-break`, `white-space`, `line-break`, `-webkit-line-break`, `-webkit-nbsp-mode`, `caret-color`, `*text-size-adjust`, plus `width`, `height`, `max-width`, `max-height` in a `style` attribute on `<img>`), so Fastmail's `<style>p.MsoNormal,p.MsoNoSpacing{margin:0}</style>` and Outlook on the web's `P {margin-top:0;margin-bottom:0;}` leave a body unstyled; no colour (so unstyled never declares colours); no `<font>` with `face` or `size`; no layout table (a `<table>` with `width`, `height`, `align`, `bgcolor`, `background`, `cellpadding`, `cellspacing` or `role="presentation"`, or a table inside a table). `styled` for every other HTML body.
- **declares_colors**: true when any of these appears: a `color`, `-webkit-text-fill-color`, `background`, `background-color` or `background-image` declaration in a `style` attribute or a `<style>` block whose whole value is not a no-colour keyword (`inherit`, `initial`, `unset`, `revert`, `revert-layer`, `currentcolor`, `transparent`, `none`); a non-empty `bgcolor` or `background` attribute on any element; a non-empty `color` attribute on `<font>`; a non-empty `text` or `link` attribute on `<body>`. A blocked remote background still counts. Plain bodies never declare colours. The reader's dark adaptation must override every property in this list (including `-webkit-text-fill-color`, which WebKit paints text with over `color`).
- **Backfill**: bodies stored before v3 have NULL facts. After each hydration batch the engine takes up to 200 of them for the account (`messageIDsMissingDesignFacts`, served by the partial index `bodies_missing_design_facts`; evicted bodies are left out, having no source left, and get their facts when fetched again), runs `HTMLSanitizer` again over the stored `html`/`text` on a background task, and writes only the three facts in one transaction (`saveDesignFacts`); rendered HTML, plain text and the full-text row are left as they are. A row it cannot read gets the reader's own assumption (styled, colours declared, not covered) so it leaves the queue. Once an account has none left the engine stops asking until the next launch.
- **covered_by_new_york**: every letter (Unicode L*) and decimal digit (Nd) of the extracted text is in New York's character set; punctuation, symbols, emoji (by the Unicode Emoji property, so U+2139 ℹ️, a lowercase letter by category, is ignored too) and marks are ignored because they fall back to the same system fonts beside either face. The character set is a range table in `Render/NewYorkCoverage.swift`, measured with `CTFontCopyCharacterSet` by `scripts/tools/newyork-coverage.swift`.

### attachment_cache (file system, not SQL)
`~/Library/Caches/SuperSparrow/attachments/<account>/<message>/<attachmentID>`; inline images keyed by content id. Each path component keeps letters, digits, `-` and `_` and percent-encodes the rest (a SHA-256 in hex when that runs past 180 characters), so an entry's name never holds a dot. A download streams into `.partial/<UUID>.partial` under the cache's root (a name no account folder can have, on the same volume) and is renamed into place once complete, so a download that fails or stops never leaves a truncated entry. Gmail writes its JSON reply beside the partial file, as `<UUID>.partial.reply`, until it is decoded. Both are removed when the download ends, however it ends; what a run cut off by quitting or a crash leaves in `.partial` is deleted before the next run's first download. The cache holds at most 1 GB on disk (`AttachmentCache.capacityBytes`): past it, entries go least recently used first by modification date, which the cache sets to now whenever it serves an entry; it trims when the engine starts and after a download that takes it past the cap, and never touches `.partial`, an entry a download in flight will read back, the entry just downloaded, or the message folder a download in flight will rename its entry into.

## Semantics

- **Unified inbox** = `SELECT … FROM conversations WHERE in_inbox = 1 [AND account_id IN (…)] [AND inbox_section = 'focused'] [AND unread_count > 0] ORDER BY COALESCE(returned_at, latest_date_ms) DESC LIMIT ?`. Paging uses `COALESCE(returned_at, latest_date_ms) < ?`. Every other view orders and pages by `latest_date_ms`.
- **Outbox** (`MailboxView.outbox`) = no conversation, and no read: its rows are `pending_sends`'s, which the app reads as summaries (spec §5.53). Both stores return an empty list for it before touching a table, so an observation of it tracks nothing.
- **Later** = `SELECT … FROM conversations JOIN snoozes USING the conversation key [WHERE account_id IN (…)] ORDER BY due_at, account_id, provider_id LIMIT ?`, never paged; the rows carry `due_at` as `ConversationSummary.snoozedUntil`.
- **All mail** = `message_count > 0 AND in_trash = 0`. **Trash** = `in_trash = 1`. **Starred** = `is_starred = 1 AND in_trash = 0`.
- **Pending operations win**: on upsert, for every incoming message that has rows in `operation_targets` with status pending/inFlight/uncertain, re-apply those operations' changes (oldest first, by `created_at` then `rowid`, the order the rows were queued in: an undo's steps are separate writes that often share a millisecond, and a tie broken by the random `id` could replay them backwards; the outbox reads pending rows in the same order, and a give-up replays the newer ones by it) on top of the incoming metadata before writing it, recording on each target row the state that operation's change now replaces (`prior_*`).
- **Confirmed operations** are deleted together with their targets (`confirmOperation`), keeping their local change. An uncertain operation a poll settles is deleted (`deleteOperation`) without being confirmed: the provider's report that follows is the truth either way. A poll settles one only when it reports every target and the operation's last attempt (its `next_attempt_at` less the backoff of its `attempts`) is older than `SyncTuning.uncertainSettleAge` (2 minutes: past a request's timeout, and below the backoff cap, so a poll between two retries can settle it): an attempt can move some targets and fail on others, and one queued offline long ago may have been sent a moment ago. An invitation's answer is never settled so, since no report shows it.
- **Failed operations** stop winning (their changes are no longer re-applied on upsert) and are never replayed. Giving one up (writing a pending, in-flight or uncertain operation as `failed`) puts back what it changed, in the same transaction: each target with a recorded prior takes the prior's roles, read and starred flags, the live operations created after it on that target are replayed on top (and their priors move to that restored state), and the conversations are refreshed, so a failed archive is back in the inbox (docs/DESIGN-LANGUAGE.md §5.7, "the row is restored locally"). Live operations created before it are already part of its prior. A prior refreshed by a poll after the change landed already shows the change, so a request that landed despite reporting failure stays applied. Targets without a prior, or no longer stored, are left as they are. The outbox prunes failed operations at the start of every drain once `next_attempt_at` has passed, one indexed lookup on `(account_id, status, created_at)`.
- **Failed-operation mark** (`conversations.failed_op_kind`, `ConversationSummary.failedOperation`, docs/DESIGN-LANGUAGE.md §5.7, §8.5). Both stores apply the same rules, inside the transaction of the write that triggers them. "An operation targets a conversation" means one of its targets is currently a message of that conversation; "newer" compares `created_at`, then `id`.
  - *Set*: writing an operation as `failed` from any other status (or inserting it failed) sets the mark of every conversation it targets to its kind, unless that conversation already carries a mark and a failed operation newer than this one also targets it (the mark names the newest failure). Writing an already failed row again changes nothing.
  - *Acknowledged*: `acknowledgeFailedOperation(conversationID:)` sets it to NULL and leaves the failed row in place. It is for the app to call once a conversation has been open for 150 ms (wired by the list stage); the SQLite store checks for a mark with a read first, so the common case never takes the writer.
  - *Confirmed*: confirming an operation (`confirmOperation`, or writing it as `confirmed`) clears the mark of every conversation it targets, unless a failed operation newer than it still targets that conversation. So a later operation that succeeds clears an older failure and an earlier one does not.
  - *Failure ended*: deleting a failed operation (how pruning removes it) or writing it out of `failed` clears the mark of every conversation it targets, unless another failed operation still targets that conversation. Every failure is kept for the same retention, so failures expire in the order they gave up: one still standing gave up after the expired one, and if the conversation carries a mark at all, after the last acknowledgement, so its mark stays. This holds whatever order operations on different messages of one conversation give up in (the runner orders operations only per message).
  - *Dropped*: deleting a live operation (`deleteOperation`, as a poll does with an uncertain one it has settled) changes no mark: it was never confirmed.
  - The mark lives on the summary row: a conversation with no summary row (every message spam, or none left) cannot be marked, and loses its mark when the row goes.
  - Known limits: the schema keeps no per-operation acknowledgement and no failure time, so where the rules compare a failure with another operation they use creation order. The kind shown is that of the newest failure by creation, not the last to give up. A confirmation clears the mark of every failure created before it, including one that gave up only after the confirmed operation was queued. The failure-ended rule assumes one retention for every failure; after a build shortens `SyncTuning.failedOperationRetention`, a mark can stay until the failures recorded under the longer retention expire. Writing a failed row back to pending (nothing does today) is not ordered by give-up time, so it can keep a mark the same way.
- **Backfill marks** (`backfill_live_marks`, `backfill_seen`). Each account syncs in two lanes: the live lane owns the change cursor and applies changes as they arrive, and the backfill lane downloads older mail behind it, paced by the provider's quota. A backfill page can therefore be fetched before a live change and written after it. Both stores apply these rules, each call in one transaction:
  - *Live marks*: while a backfill runs, the engine marks every message the live lane writes or deletes (`markLiveChanges`), and marks it before the `upsertMessages` / `deleteMessages` that applies the change, never after. The mark is its own transaction, so only a mark that commits first closes the window in which a backfill write or sweep could run between the live write and its mark: marked after, a stale page could bring back a just-deleted message or overwrite a newer one, and a sweep could delete mail that just arrived (the cursor has already moved past it). A mark whose live write then fails is harmless: the backfill skips that message, and the live lane writes it when it retries the page, because the cursor moves only after the write. A later mark replaces an earlier one's `deleted` flag; within one call an id both written and deleted is marked deleted, the order a changes page is applied in (upserts, then deletions).
  - *Backfill writes only add*: `writeBackfillMessages` drops every message that has a live mark and, unless it is refreshing (a reconcile, below), every message already stored, then writes the rest through the same path as `upsertMessages` (full-text rows, conversation summaries, contacts, "Pending operations win"). The mark check and the write share the transaction, so a live change marked before it is written either is marked by the time the page checks (and is skipped) or is written after the page, waiting for its transaction, and overwrites it. This is why the marks exist: a page fetched before a live change must neither overwrite it (undo a read, an archive, a new label) nor bring back a message the live lane deleted. A repeated id in one page is written once, as its last copy. `backfillSkippableIDs` answers the same question before the backfill fetches metadata, so quota goes only to messages it will write; it is advisory and the write checks again. A search of the server (docs/ARCHITECTURE.md, "Server search") writes its hits through the same two calls, never refreshing: a hit already stored changes nothing, and one the live lane deleted while a backfill runs is not brought back. It needs no table of its own: what it found is an ordinary message row, indexed by its snippet until its body arrives, and the list names its conversations in the query (`ConversationQuery.serverMatches`), not in the store.
  - *Reconcile*: a rejected change cursor no longer wipes the mailbox. The live lane takes a fresh cursor and the newest page, and a reconciling backfill (`BootstrapState.reconciling`) lists the whole mailbox again, refreshing stored messages (`refreshExisting`, marked ones still skipped) and recording every id it lists in `backfill_seen` (`markBackfillSeen`).
  - *Finish*: `finishBackfill` ends the account's backfill. After a reconcile that listed everything (`sweepUnseen`), it first deletes the account's messages whose id is in neither table and that no live (pending, in-flight or uncertain) operation targets (a message the live lane writes is marked before it is stored, so the sweep never sees it unmarked), through the message delete so the full-text index and conversation summaries follow: the provider no longer has them, and this removes them without wiping the mailbox. A message a live operation targets stays, since the store cannot tell whether the provider still has it; the engine asks the provider about those targets just before the sweep (`lookUpMetadata(for:)`) and deletes the ones it no longer knows (one it will not return on its own stays), because a deletion in the gap the reset covers sat in the expired history, so neither a later poll nor the operation's outcome would ever remove them. "Listed everything" means everything the enumeration covers: where it leaves out mail the store holds and nothing after the reset would report again (Gmail's Trash and Spam, `MailProvider.hasMailOutsideEnumeration`), the engine records those ids as seen too (`mailOutsideEnumeration`, ids only) before the sweep, so what Gmail still keeps stays and only what it purged in the gap goes. Then it deletes all of the account's rows in both tables, so marks only ever describe the backfill that is running.
  - `wipeMailData` clears both tables for the account; deleting the account removes them (the wipe, and the foreign keys).
  - No observation reads either table, so a mark never wakes the list.
- **Queued lookups** (`queued_lookups`). A folder the provider reports gone (a Graph folder whose delta answers 404, or one two folder walks in a row did not find) takes its mail with it if it was purged, and no delta reports that. `queueLookups` queues every stored message of the account in those folders (`folder_id`; a scan, since a folder goes rarely and an index would cost every message write, read on a reader so it never holds the writer; the write inserts the messages it found by key, each still in one of those folders), keeping the tries of one already queued; the live lane writes it before it saves the cursor that moved past the report. `queuedLookups` hands out up to a limit in id order with their tries, and `settleQueuedLookups` drops the settled ones and counts a try against the rest, in one transaction. The lookups themselves, and what each answer means, are the engine's (docs/ARCHITECTURE.md, SSGraph). `wipeMailData` clears the account's rows; deleting the account removes them (the foreign key).
- **Snoozes** (`snoozes`, `conversations.returned_at`, spec §5.45). Both stores apply these rules, each call in one transaction:
  - *Snoozing*: `setSnoozes(_:enqueueing:at:)` applies and queues its operations as `enqueue` does (the window passes the archive of whatever is in the Inbox; an unsubscribe of a snoozed conversation, its request with the snooze's end), then writes each change: a date inserts the snooze or replaces its time and `created_at` (a reschedule), nil deletes it, and a `returnedAt` (an undo of the Archive, Move to Trash or snooze that took a conversation back from Later out of the Inbox) sets `returned_at` to it where the conversation is now in the Inbox and its newest mail is older, the rule the refresh keeps the mark by. A date is written only for a conversation that has a summary row with `in_inbox = 0` and `in_trash = 0` once the operations are applied, and whose messages other than the user's own copies (outside the Inbox, with the sent or drafts role) are not all in the Trash or Spam, so a snooze always stands for mail put away (`Snooze.canHold` states the rule in Swift; the in-memory store uses it, and the window asks it of its selection as snoozing would leave it, so L beeps rather than toast a snooze that would be dropped). That last rule is for the user's own copies, which Move to Trash leaves in Sent Items and Drafts on Microsoft and Mark as Spam leaves on both providers, so `in_trash` stays 0 and the summary row stays.
  - *Returning*: `returnDueSnoozes(at:dueBy:limit:operations:)` takes the snoozes due by `now`, soonest first, and for an account in `dueBy` only those due by its date (the engine holds back a time the account has not checked for mail past yet, docs/ARCHITECTURE.md "Later"; the batch is counted after those are left out); for each it deletes the row, reads the conversation's messages (oldest first), applies and queues the operations the caller makes from them (the engine: move to the Inbox the messages that are not in the Trash or Spam, on Microsoft leaving the user's own copies in Sent Items and Drafts as Move to Inbox does, and mark the latest of those unread, a millisecond later so the outbox replays them in that order), and, after all of them, sets `returned_at = now` where the conversation is now in the Inbox and its newest mail is older. A due snooze whose conversation has no messages left is just deleted. A read checks first whether anything is due, so a look with nothing due never takes the writer.
  - *Ending early*: every summary refresh deletes the snooze of each touched conversation that is back in the Inbox (⇧I, a drop, another device reporting it there, new mail delivered to the Inbox, a given-up archive), in the Trash or Spam (everything but the user's own copies: the rule `setSnoozes` writes by, except that a spam message whose `date_ms` is after the snooze's `created_at` counts for nothing, as it never ends a snooze on arrival either, so a reply the provider files in Spam leaves a follow-up on the user's own message snoozed; `setSnoozes` counts every spam message, never looser than the rule that keeps the snooze), or gone (no message outside Spam). And an upsert of a message new to the store deletes its conversation's snooze when `created_at` is before the message's date, unless the message is the user's own (sent, a draft) or spam: mail from someone else ends a snooze even when a provider rule keeps it out of the Inbox, and older mail the backfill lists does not. Nor does mail the mute or a sender rule covers ("Arrival rules"): in a muted conversation, or from a sender the account has a row for in `sender_rules` (on `upsertMessages`, whatever the row's `sync`: a rule on its way to the server or being deleted there is still one the user set), whatever became of it, so a reply the mute archives, or a blocked sender's message the server put in the Trash before it arrived, leaves the conversation snoozed, and it comes back at its time; the refresh still ends the snooze where the conversation is back in the Inbox, in the Trash or Spam, or gone.
  - *The return mark*: a refresh carries `returned_at` over only while the conversation is in the Inbox and the value is later than its newest mail; the summary row going (no messages) takes it too.
  - `wipeMailData` keeps the snoozes (the user's intent, like queued operations) and drops the summary rows with their marks; `snoozes()` and its observation join `conversations`, so a snooze whose mail is gone stays out of sight until the mail is back. Deleting the account removes them (the foreign key; the in-memory store mirrors it).
- **Arrival rules** (`conversations.muted`; roadmap Q3.7 Mute). Mail new to the store (no row for its id yet) in a muted conversation is archived in the transaction that stores it, through the ordinary operation queued in that same transaction, as "Pending operations win" replays live ones: no observer sees the row in the Inbox, and the outbox replays the change so every device agrees once it lands. Both stores apply this rule (`ArrivalRules`, `ArrivalRule.change`). Sender rules take no part since v23: they live on the server ("Sender rules"), which archives or trashes the sender's mail before this Mac sees it, so the store stores it where the provider put it and queues nothing for a rule, whatever its state (a rule still on its way to the server takes nothing either; its mail arrives in the Inbox until the server has it).
  - *Which change*: on the message as stored (the provider's report with older live operations replayed), spam is left alone; in the Inbox, the mute archives it, whoever sent it (the user's own copy too).
  - *Which messages*: the mute takes every message of the conversation in the Inbox (and not in the Trash or Spam), older ones too, so a muted conversation moved back to the Inbox (⇧I, another device) leaves it again with its next mail. Per account one Archive operation, created now. Mail a server rule archived, in a conversation the Inbox still holds for other mail, leaves that conversation in the Inbox, and its summary, built from every message outside the Trash, takes the archived message in as it takes any (its date, snippet and unread count); only the notification is held back, by the window (`NewMailNotifier`), which never notifies mail outside the Inbox.
  - *Snoozes*: the rule is asked before the snooze rule for mail new to the store, and mail it or the mirror covers (`ArrivalRule.keepsSnooze`: a muted conversation's, or mail from a sender with a row in `sender_rules`) never ends a snooze ("Snoozes", *Ending early*).
  - *Which writes*: `upsertMessages` (a poll's changes, a head page) applies the mute and reads the mirror for the snooze; `writeBackfillMessages` (the backfill, a search of the server) applies the mute alone, since its mail is old, not arriving. A report of a message already stored is never an arrival, so the mute never fires twice and a given-up archive is not redone.
  - *Priors*: the messages are written as reported first, then the operation is enqueued as a user action is, so each target's prior is the provider's report and a give-up puts the message back where the provider has it.
  - *Cost*: once per write, the accounts with anything muted (the partial index) and with any sender rule row (a handful of rows); then, only for mail new to the store in those accounts, one primary-key probe of `conversations` and of `sender_rules`. A write with neither costs two small reads.
  - `setMuted(_:conversations:enqueueing:returnMarks:)` applies and queues its operations as `enqueue` does (muting archives what is in the Inbox), then writes the flag, in one transaction. An undo of a mute passes the return marks its archive ended, set by the rule `setSnoozes` sets a `returnedAt` by: only where the conversation is now in the Inbox and its newest mail is older.
- **Sender rules** (`sender_rules`; roadmap Q4.2, docs/ARCHITECTURE.md "Rules"). The server is the single source of truth: a sender rule is a Gmail filter or an Outlook inbox rule, which the provider runs as mail arrives whether or not this Mac is on. The table is the mirror of the server's sender rules plus the user's changes on their way there, which the engine's rules lane sends; the UI shows every row with its state and never calls a provider. Both stores apply these transitions (`SenderRuleMirror`, shared), each call in one transaction:
  - *The user's change* (`setSenderRule(_:for:accountID:enqueueing:at:)`, which first applies and queues its operations as `enqueue` does: a rule takes its sender's mail where it was set from, once, since a server rule acts only on mail that arrives after it exists, `SenderRule.Action.change(for:)`). Setting a rule on an address with no row inserts it `creating`; on a `creating` row it changes the action and stays `creating`; on a `saved` or `replacing` row with another action it becomes `replacing`, keeping the server ids; on a `deleting` row it becomes `replacing` whatever the action (the row never claims a rule the server lacks: the engine's read finds the server's own rule and adopts it when it is the same, deleting nothing). Removing it deletes a `creating` row at once (the server never had it) and makes a `saved` or `replacing` row `deleting`. The same action again, or removing a rule being deleted, changes nothing. Every change sets `created_at` to the call's time.
  - *A read of the server* (`replaceServerSenderRules(accountID:with:readAt:)`): the server's sender rules, one entry per server rule, fold by address (every id, the block when any of them blocks). The `saved` rows become that list: a rule changed or added elsewhere is changed or added here (a new row's `created_at` is `readAt`; a known row keeps its own), one gone goes. Rows on their way stay as they are, except that a `creating` row whose identical rule (same address and action) the server now has becomes `saved` with its ids, and a `deleting` row none of whose ids the server still has goes, or becomes the rule the server holds for the address now. Nothing is written for an account the store no longer has (removed while the read was on its way).
  - *What the engine did* (`settleSenderRule(for:accountID:_:)`, a `SenderRuleOutcome` stating a fact about the server, applied to the row as it stands then, which the user may have changed meanwhile). `written(action, serverIDs, deleted)`: the row's ids become its own and the new ones, less the deleted; a `creating` or `replacing` row that still wants that action and holds no other id is `saved`, any other stays (or becomes) `replacing` with the ids it still has to deal with (`creating` if none); a `deleting` row keeps the new ids to delete, or goes when none are left. `deleted(serverIDs)`: the ids leave the row; a `deleting` row with none left goes; a `replacing` or `saved` row with none left is `creating` again (the user wants the rule; what the server had is gone). `refused(attempted, serverHas)`, ignored when the row has moved to another state since: a create is given up (the row goes); a delete or a replacement is put back as the server has it, `saved` with `serverHas` (the action the server holds for the address then, as the engine knows it from its read and its own writes since, folded as a read folds it), or goes when the server holds nothing it can show. The call returns false, changing nothing, when there is no row: the engine then deletes what it just wrote on the server.
  - *Reading*: `senderRules()` lists every row, `pendingSenderRules(accountID:)` the account's rows not `saved`, oldest `created_at` first, then by address.
  - Removing the account deletes its rows (the foreign key; the in-memory store mirrors it); the rules stay on the server, where a new sign-in reads them again.
- **Invitation answers** (`messages.invitation_reply`). Enqueueing an `answerInvitation` operation writes the answer on its target in the same transaction (`applying` sets it; the flags write carries it). Upserts leave the column alone, so the recorded answer stands through every poll, live operation or not; replaying live operations on an upsert re-applies a live answer, which changes nothing stored. Giving one up puts back the answer its change says it replaced, then replays the live operations created after it on that target, so a newer answer still wins; each newer live answer is rewritten in the same transaction to name the answer in place before it in that replay (the one the given-up answer replaced, for the first), since the given-up one never went out and a later give-up must not put it back. Confirming or deleting it keeps the answer. The runner deletes an answer a newer answer on the same message replaces, before anything is sent, after saving the newer one with the answer the first replaced one replaced; it deletes the newer one too when nothing deleted was ever tried and it repeats that answer.
- **Calendar events** (`calendar_events`, docs/ARCHITECTURE.md "Calendar"). The UI reads events only from the store; the engine writes what it reads from each account's main calendar and replays what was set aside or removed here. Both stores apply these rules (written once, as functions both call, on `CalendarEventTable`), each call in one transaction:
  - *Reading*: `calendarEvents(in:accountIDs:)` returns the events that overlap the interval (`start_ms < end AND end_ms > start`, and an event of no length at the interval's start: `CalendarEvent.overlaps`, compared in stored milliseconds), of the accounts asked for (nil: every account; an empty list: none), ordered by `start_ms`, `end_ms`, `id`: one range of the time index, never a sort. Declined events and events being deleted are listed; callers draw only `isShown`. `observeCalendarEvents(in:)` reads it again for every account after every write to the table and delivers only a changed list, first the current value, on the main thread; it reads no other table, so mail arriving, a body saved, a time found in it or a wipe of the mail never wakes it, and a write outside its interval delivers nothing.
  - *A read of the calendar*: `replaceCalendarEvents(_:accountID:window:)` writes what one read of the account's calendar found for the window. Each read event is merged first. One whose client key a stored row of the account carries is that row: the provider's copy of time set aside here, created even when the reply to the create was lost. It takes the row's id and mail; the row becomes `synced` (from `creating`, or from `failed`: the provider has it after all) or stays `deleting`, now with the provider's id, for the engine to delete. Any other event is inserted, or replaces the row with its id, as `synced`; but a `creating` row with its id is kept as it is, and a `deleting` one stays `deleting`, taking what the read says of it. A client key claims one row per read: the first event listed with it is merged by it, and a later one with the same key (an occurrence of a block someone made repeating elsewhere, whose occurrences all carry the series' key) is stored without it under its own id, as any event is, so no occurrence overwrites another. A merged row identical to the stored one is not written, so a read every two minutes that finds nothing new rewrites nothing. Then every `synced` or `deleting` row of the account that overlaps the window and was not listed is deleted: the provider no longer has it (a `synced` one deleted elsewhere, a `deleting` one the engine's delete reached, a tombstone whose create never made a copy). A `failed` row, which the provider never had, stays with its mark until the user removes it. Last, the history goes: every `synced` row of the account that ended more than 30 days before the window kept around now (`CalendarWindow.around`, the store's clock), or before the read's own window when that starts earlier (days behind the window the app asked to see, kept until the next read of the window), is deleted, through the time index, so the table, the range reads and every refresh's sweep stay the size of the window. Rows waiting for the provider or marked `failed` are never pruned. Other rows outside the window, and other accounts' rows, are left alone. A read for an account the store no longer has writes nothing.
  - *Time set aside*: `addCalendarEvent` inserts the event as `creating` with no provider id, giving it a client key when it has none, and stamps `queued_ms`; it throws `StoreError.conflict` when the id is taken and `StoreError.notFound` for an account the store does not have. `settleCalendarEvent(id:created:)` writes the provider's copy over the `creating` row, keeping the row's id, and its mail and key where the copy has none, and returns true. A row a read already settled to that very copy (`synced`, same provider id) is left as it is and answers true too. A tombstone (removed while it was being created, no provider id yet) takes the copy's provider id and stays `deleting` and hidden, and answers true: the engine deletes the copy at once, and should that fail or the app quit, the id waits in the row for the next turn. Anything else (the row gone, or in another state) answers false and changes nothing: the engine then deletes the copy it just made. `failCalendarEvent` marks a `creating` row `failed` (any other is left alone); it is drawn with the failed mark until it is removed, which deletes it at once (a read that finds it made after all, by its client key, settles it instead).
  - *Removing*: `removeCalendarEvent(id:)` deletes a `failed` row at once (the provider refused it: it made nothing), marks a `synced` one `deleting` (stamping `queued_ms`), leaves a `deleting` one as it is, and returns the row as it was, for the undo; nil when there was none. A `creating` row becomes a tombstone: `deleting` with no provider id, under the same id and client key, never drawn, since its create may have reached the provider with the reply lost and only the key finds that copy. The engine sends nothing for it; the next read either lists the copy by its key, which fills in the provider id for the engine to delete, or does not, and sweeps it. `settleCalendarEvent(id:created: nil)` deletes a `deleting` row once the provider has deleted it and answers true; any other answers false and changes nothing.
  - *Undo*: `restoreCalendarEvent` puts back what `removeCalendarEvent` returned. A row still `deleting` goes back to `synced`, and a tombstone with no provider id back to `creating` under its own id and key, so the create sent again finds any copy the first one made (Google answers 409 and the copy is read back; Graph matches the `transactionId`) rather than making a second. A row that went is inserted again as `creating`, which the engine creates, under a new client key (the engine deleted the copy, whose key Google keeps reserved, or no copy was found): under its own id when the provider never had it (no provider id); under a new local id too, without the provider's id, links, UID or time of change, when it had, since Google keeps a deleted event's id reserved. Any other row is left as it is, so a second undo changes nothing. It returns the row as it now stands, and throws `StoreError.notFound` when the row went with its account.
  - *Replaying*: `pendingCalendarEvents(accountID:)` lists the account's `creating` and `deleting` rows by `queued_ms`, then id: what the engine creates or deletes before it reads the account's calendar (a tombstone with no provider id is listed and skipped: the read decides it).
  - *Answers*: `answerCalendarEvents(_:invitationUID:accountID:near:)` writes an answer given on this Mac on the calendar's copy of the invitation at once (store first: a decline leaves the day column before the provider has it): each `synced` row of the account whose `invitation_uid` names the invitation (`InvitationUID.matches`, which sets aside the date Exchange writes into each occurrence's UID) and that the user did not organize takes the answer as its `response`, or only the occurrence whose start is nearest `near` when given (an answer to one occurrence). The calendar's next read writes what the provider says.
  - `wipeMailData` keeps the account's events: the calendar is not mail, and a reset of the mail cursor says nothing about it. Deleting the account removes them (written out before the account row goes, so the observation sees it, besides the foreign key; the in-memory store mirrors it).
- **Mail times** (`mail_times`). `saveMailTimes(_:for:)` replaces the message's times in one transaction (an empty list clears them), each saved under the message it is saved for, in the order given; the times of a message the store does not hold (a poll deleted it while its body was read) are dropped, as its body would be. `mailTimes(in:)` returns the times of the conversation's messages ordered by start, then the message's id, then the order found, the instant to the millisecond and the length to the second. They go with their message, never with its body: deleting the message (a poll, a backfill's sweep), `wipeMailData` and deleting the account remove them (the foreign key; the in-memory store mirrors it), an eviction keeps them, and a message the provider reports in another conversation takes them there. Both stores apply these rules.
- **Conversation key** is the provider's thread id scoped to the account. Never re-thread across accounts.
